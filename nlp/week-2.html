1. Week overview and learning objectives

Week 2 introduces tokenization and the conventions used by spaCy. The week connects conceptual NLP preprocessing with practical Python usage and real-world tokenizer design.

By the end of the week, you should be able to:

  • explain why spaCy is used for production NLP;
  • describe a language-processing pipeline and its components;
  • distinguish spaCy’s processing and container classes;
  • load a pretrained language model and create a Doc;
  • explain and perform word, sentence, character, whitespace, n-gram, and subword tokenization;
  • customize spaCy’s tokenizer with special cases;
  • debug and test tokenizer behavior;
  • obtain lemmas, POS tags, dependencies, named entities, and sentence boundaries;
  • evaluate preprocessing and tokenizer choices for a particular task, language, and deployment constraint;
  • explain the trade-offs between throughput, maintainability, memory use, and domain accuracy.

2. Why spaCy?

2.1 Definition and positioning

spaCy is a free, open-source, industrial-strength Python library designed for NLP. Unlike libraries used mainly for academic demonstrations, it is intended for production and end-to-end NLP application development involving complex document and data understanding.

Important properties emphasized in the lectures:

  • Fast: core performance-sensitive modules are implemented in C/Cython, allowing efficient processing of large, unstructured text collections.
  • Production oriented: designed to ship working code and process real-world data in reasonable time.
  • Pretrained models: supplies statistical language models trained on large corpora (for example, web or Wikipedia-like data).
  • Multilingual: supports 60+ languages, although the quality and completeness vary by language.
  • Extensible: open-source code is hosted publicly; developers can report bugs, propose features, and contribute.
  • Strong ecosystem: professionally maintained code, documentation, examples, and a developer community.

The live lecture contrasted spaCy with Stanford CoreNLP, ZPar, and NLTK. The illustrative benchmark values shown included approximately 0.2 ms for spaCy tokenization, compared with 0.18 ms for CoreNLP, 1 ms for ZPar, and 4 ms for NLTK; for tagging, the slide cited approximately 1 ms for spaCy versus 10 ms for CoreNLP. Treat such numbers as workload- and hardware-dependent illustrations, not timeless universal benchmarks. The intended exam point is that speed is a major reason for spaCy’s industry adoption.

2.2 Model naming convention

Example model names:

  • en_core_web_sm
  • en_core_web_md
  • en_core_web_lg

Interpretation:

  • en — English;
  • core — core NLP capabilities;
  • web — trained on web text;
  • sm, md, lg — small, medium, and large model sizes.

A larger model generally offers more resources/capability but uses more memory and storage. A small model is lighter. The appropriate choice depends on accuracy, memory, latency, and deployment constraints.

3. spaCy’s language-processing pipeline

3.1 What is a pipeline?

Every NLP application performs several processing steps. A language-processing pipeline is the ordered sequence in which these steps operate on text. Each component receives the current Doc, reads or adds annotations, returns the processed Doc, and passes it to the next component.

Conceptual flow:

Raw text
  → Tokenizer
  → Tagger / morphological analysis / lemmatizer
  → Dependency parser
  → Named-entity recognizer
  → Optional rules, categorizer, or custom components
  → Annotated Doc

The input may be one sentence, multiple sentences, a paragraph, a complete document, or even a book. Tokenization is first because subsequent analysis requires meaningful, smaller units rather than an undifferentiated character sequence.

3.2 Basic code pattern

import spacy

nlp = spacy.load("en_core_web_md")
doc = nlp("I went there.")

What happens:

  1. import spacy makes the library available.
  2. spacy.load(...) loads a pretrained model and returns a Language instance, conventionally named nlp.
  3. The Language object is the text-processing pipeline.
  4. Calling nlp(text) tokenizes and runs enabled components behind the scenes.
  5. The result is a Doc containing tokens and the annotations the loaded model can produce—such as POS tags, lemmas, dependencies, and entity labels.

The pipeline’s behavior depends on the statistical model and its capabilities. This is why the model must be chosen and loaded before expecting trained annotations.

3.3 Process the text once

Efficient approach:

doc = nlp(text)
for token in doc:
    print(token.text, token.pos_, token.dep_, token.lemma_)

Do not call nlp() independently for each isolated word unless that is truly the task:

# Usually inefficient and context-destroying
for word in words:
    nlp(word)

Running the full pipeline once preserves sentence context and avoids repeated computation. Reading token.pos_ or token.dep_ later does not rerun the model; these annotations are already stored in the Doc.

3.4 Inspecting enabled components

nlp = spacy.load("en_core_web_sm")
print(nlp.pipe_names)

An illustrative pipeline may contain:

  • tok2vec (token-to-vector representation),
  • tagger,
  • parser,
  • attribute_ruler,
  • lemmatizer,
  • ner.

Different models can expose different components.

3.5 Blank versus trained pipelines

nlp = spacy.blank("en")

A blank English pipeline provides language-specific defaults and a tokenizer, but does not automatically contain trained POS tagging, parsing, or NER components. Those must be explicitly added and trained, or obtained by loading a trained package.

4. spaCy processing classes and their duties

Class/component Duty
Language The overall text-processing pipeline; normally loaded once per process and passed around the application as nlp.
Tokenizer Segments raw text and creates a Doc with discovered token boundaries.
Lemmatizer Determines the dictionary/base form of words.
Morphology / morphological analysis Assigns linguistic features such as lemma, noun case, and verb tense, informed by the word and POS tag.
Tagger Annotates part-of-speech tags on the Doc.
Dependency parser Annotates syntactic dependency relations and usually supplies sentence boundaries.
Entity recognizer (ner) Detects and labels named entities such as people, products, organizations, locations, money, dates, or times.
Text categorizer Assigns categories or labels to an entire Doc.
Matcher Matches token sequences using token-based patterns, broadly analogous to regular expressions over tokens.
PhraseMatcher Matches sequences based on stored phrases.
EntityRuler Adds entity spans using token patterns or exact phrase matches.
Sentencizer Implements rule/custom sentence-boundary detection without requiring the dependency parser.

Each component has a well-defined task. A custom component may read, modify, or add annotations and can influence later components. Extra components execute for every document, so they can improve task accuracy while increasing latency, testing, and maintenance.

5. spaCy container and helper classes

5.1 Core containers

Object Meaning
Doc Central container for a processed text and its linguistic annotations; owns the token sequence and token properties.
Span A slice of a Doc, such as a sentence or named-entity span.
Token An individual contextual token—a word, number, punctuation mark, currency symbol, or other meaningful item.
Lexeme A context-free vocabulary entry or word type, as opposed to a particular token occurrence. Because it has no sentence context, it has no contextual POS or dependency label.
Vocab The shared language vocabulary, string store, and lexical attributes used by other objects.

The two backbone structures emphasized were Doc and Vocab.

5.2 Shared vocabulary and memory efficiency

spaCy avoids storing the same text string repeatedly. Unique strings are stored in a shared Vocab/StringStore, and tokens refer to them through integer hashes.

Token → integer hash → shared Vocab/StringStore → string

Benefits:

  • fewer duplicate strings in large corpora;
  • lower memory use;
  • faster integer comparisons and lookups;
  • better scalability across many documents.

The mapping is bidirectional in concept:

integer hash ↔ string

5.3 Useful token attributes

Attribute Meaning/use
token.text Original surface string.
token.pos_ Coarse grammatical category such as NOUN, VERB, ADJ, ADV, or PRON.
token.dep_ Dependency relation such as ROOT, nsubj, dobj, amod, or prep.
token.lemma_ Dictionary/base form.
token.norm_ Normalized form.
token.shape_ Abstract orthographic pattern.
token.is_stop Boolean: whether the token is in spaCy’s stop-word list.
token.is_alpha Boolean: whether the token consists of alphabetic characters. The lecture loosely called this “alphanumeric”; the precise spaCy meaning is alphabetic.
token.is_punct Boolean: whether it is punctuation.
token.is_space Boolean: whether it is whitespace.

Example:

for token in doc:
    print(token.text, token.is_alpha, token.is_punct, token.is_space)

If the token is Apple, expected values are approximately True, False, False. A final period normally appears as its own punctuation token.

6. Text preprocessing

6.1 Definition and importance

Text preprocessing is cleaning and preparing text before feeding it to an NLP model, ML model, or analysis algorithm. Poor-quality data produces poor-quality outputs (“garbage in, garbage out”), because noise present in training data can be encoded by the model.

Typical operations:

  • noise reduction;
  • standardization/normalization;
  • tokenization;
  • stop-word removal;
  • stemming;
  • lemmatization;
  • handling numerical data;
  • handling special characters, Unicode, URLs, emojis, and other artifacts.

Public or social-media data is often unstructured and noisy. Images, URLs, emojis, mixed languages, unwanted messages, and irregular symbols must be assessed—not automatically deleted. What counts as noise depends on the task.

6.2 Cleaning is task dependent

There is no universally correct sequence of lowercasing, punctuation removal, stop-word removal, stemming, or lemmatization.

Lowercasing reduces vocabulary and makes matching easier, but can destroy information:

  • Apple may mean the company;
  • apple may mean the fruit.

Stop-word removal can help information retrieval, topic modelling, document clustering, search, or keyword extraction, but may damage sentiment analysis, translation, QA, or inference. Removing not from “not good” reverses the meaning.

Numerals and special characters may be irrelevant in one task but essential in another. For example, $175.50, Q3 FY2024, and 31-Mar-25 are highly informative in finance.

6.3 Early decisions propagate

Raw text → Cleaning → Tokenization → Embeddings/features → Model → Prediction

An early boundary or normalization error affects all later stages. Poor tokenization cannot easily be repaired downstream.

7. Tokenization fundamentals

7.1 Definition

Tokenization is the process of splitting text into tokens. A token is an atomic, meaningful unit—the smallest useful unit of semantics for the intended analysis.

Tokens may be:

  • words;
  • numbers;
  • punctuation;
  • currency symbols;
  • dates;
  • entity names;
  • meaningful multiword phrases;
  • subwords;
  • characters.

Example:

I love natural language processing!

Possible tokens:

I | love | natural | language | processing | !

Tokenization structures otherwise unstructured text, permitting feature extraction, statistical modelling, and later NLP analysis.

7.2 General tokenization operations

Depending on the tokenizer and task, the process may include:

  • splitting into words or sentences;
  • deciding how punctuation should be separated;
  • handling contractions such as can't;
  • handling possessives such as tomorrow's;
  • handling hyphenated words;
  • preserving or normalizing special-domain expressions.

The video used “I can’t wait for tomorrow’s meeting” to show that a superficially simple sentence contains nontrivial decisions around contractions and apostrophes.

7.3 Benefits

  1. More manageable representation: converts large text into individual analyzable units and relationships.
  2. Dimensionality/complexity control: depending on representation, helps focus on meaningful units and supports efficient large-volume processing.
  3. Feature extraction: tokens support sentiment analysis, topic modelling, NER, and many other tasks.
  4. Mathematical modelling: tokens can be encoded numerically and used with statistical or ML algorithms for insight, prediction, optimization, and data-driven decisions.

Tokenization is not merely a fixed preliminary routine; it is an architectural design decision affecting vocabulary size, unknown-word handling, memory, sequence length, speed, and downstream accuracy.

8. Types of tokenizer

8.1 Word tokenizer

Treats individual words as tokens, often initially using whitespace boundaries.

Machine learning is useful
→ Machine | learning | is | useful

Advantages:

  • simple and interpretable;
  • shorter sequences;
  • often fast;
  • relatively rich semantics per token.

Limitations:

  • large vocabulary;
  • poor handling of unseen or out-of-vocabulary (OOV) words;
  • naive whitespace splitting mishandles punctuation, contractions, citations, hashtags, and languages without spaces.

8.2 Sentence tokenizer

Splits a document into individual sentences, each treated as a unit.

Useful for summarization, translation, review processing, document indexing, sentence classification, or long-document chunking.

8.3 Whitespace tokenizer

Splits at spaces, tabs, line breaks, and related whitespace. It is a simple baseline rather than a robust universal solution.

8.4 Character tokenizer

Treats every character as a token.

Hello → H | e | l | l | o

Advantages:

  • virtually eliminates OOV words;
  • robust to misspellings;
  • can be relatively language-independent;
  • useful when character-level patterns matter.

Limitations:

  • very long sequences;
  • weak semantics per token;
  • higher sequential computation and often slower processing.

8.5 N-gram tokenizer

An n-gram is a continuous sequence of n items, usually words or characters.

  • unigram (n = 1): computer;
  • bigram (n = 2): computer networks;
  • trigram (n = 3): computer network security;
  • four-gram, five-gram, etc.

The lecture’s main point was that related words can be grouped into a meaningful unit. In typical sliding n-gram extraction, the window advances one item at a time, though task-specific chunking may instead use non-overlapping groups.

8.6 Subword tokenizer

Breaks words into recurring meaningful pieces:

unbelievable → un | believe | able

Examples: Byte Pair Encoding (BPE), WordPiece, and SentencePiece.

Advantages:

  • greatly reduces OOV failures;
  • balances vocabulary size and sequence length;
  • handles rare or morphologically complex words;
  • widely used in Transformers and multilingual NLP.

Limitations:

  • more complex;
  • sequences are longer than whole-word sequences;
  • additional computation may be needed.

8.7 Strategy comparison

Property Word Subword Character
Vocabulary size Large Medium/balanced Very small
OOV handling Poor Excellent Excellent
Sequence length Short Medium Long
Semantic information per token High Moderate Low
Typical speed Fast Moderate Often slower
Main strength Interpretability Coverage–efficiency balance Robustness to any spelling

The correct strategy depends on the task, language, spelling variation, expected inputs, memory, latency, computation, and semantic requirements. There is no universally best tokenizer.

Practical guidance:

  • noisy social-media/OCR text: character or subword units are often robust;
  • modern language models: usually subword tokenization;
  • memory-constrained device: consider model size, vocabulary storage, and sequence length together—“simpler” is not automatically better;
  • phrase detection: n-grams or phrase rules;
  • sentence-level classification: sentence segmentation followed by word/subword tokenization.

8.8 Libraries/tools mentioned

  • NLTK (Natural Language Toolkit);
  • spaCy;
  • Stanford CoreNLP;
  • Hugging Face Transformers.

9. spaCy tokenization in practice

9.1 Basic token iteration

import spacy

nlp = spacy.load("en_core_web_sm")
doc = nlp(
    "Natural language processing is a subfield of artificial intelligence."
)

for token in doc:
    print(token.text)

The final period is normally a separate token. Punctuation has linguistic value and should not be reflexively discarded; for example, ! can signal emphasis or affect sentence interpretation.

9.2 POS, lemma, and dependency together

for token in doc:
    print(token.text, token.pos_, token.dep_, token.lemma_)

POS tags are context-dependent. duck is a noun in “The duck swims” but a verb in “Duck quickly!”. The tagger must map contextual ambiguity to a consistent annotation so that downstream parsing can operate.

Dependency parsing represents grammatical relations, often conceptualized as a dependency tree. It relies on correct tokenization and POS information. An early error can lead to an incorrect tree.

Example in aspect-based sentiment:

The battery is good, but the camera is disappointing.

A dependency parser can associate good with battery and disappointing with camera, which is more useful than merely finding positive and negative words.

10. Customizing the spaCy tokenizer

10.1 Why customization is necessary

Medicine, insurance, finance, law, and other domains contain characteristic abbreviations, entities, contractions, dates, citations, symbols, and phrases that need special boundaries.

Representative financial examples:

  • buy 500 AAPL @ $175.50
  • 31-Mar-25
  • Q3 FY2024

Representative domain entities:

  • healthcare: HbA1c;
  • finance: NASDAQ-100;
  • manufacturing: ISO-9001.

10.2 Data-first workflow

Do not begin by inventing rules in isolation.

  1. Collect representative production examples.
  2. Record the expected token sequence for each input.
  3. Include abbreviations, contractions, punctuation, currencies, dates, hashtags, citations, and edge cases.
  4. Build a small regression test suite.
  5. Implement rules.
  6. Run the suite after every tokenizer modification.

A test suite makes behavior explicit, repeatable, and safe to change. Without expected outputs, one cannot reliably tell whether a “fix” broke another pattern.

10.3 ORTH special cases

The videos customized lemme to become two tokens, conceptually lem and me:

import spacy
from spacy.symbols import ORTH

nlp = spacy.load("en_core_web_md")

special_case = [
    {ORTH: "lem"},
    {ORTH: "me"},
]
nlp.tokenizer.add_special_case("lemme", special_case)

print([w.text for w in nlp("lemme that")])
# ['lem', 'me', 'that']

ORTH means the token’s orthographic/surface text.

With surrounding punctuation:

print([w.text for w in nlp("lemme!")])
# ['lem', 'me', '!']

The tokenizer incrementally strips applicable punctuation and applies special-case logic to the remaining substring. If the special case itself includes punctuation, it can take precedence:

nlp.tokenizer.add_special_case(
    "lemme?",
    [{ORTH: "lemme?"}],
)

Now lemme? may remain one exact token according to the registered rule.

10.4 Specific versus general rules

In rule systems, specific cases should take precedence over broad patterns. For example, preserve Dr. before applying a generic “split at period” rule. Otherwise, a broad rule may consume or damage a specialized expression.

10.5 ORTH versus NORM

  • ORTH preserves the exact original surface form, e.g. Dr..
  • NORM provides a standardized analysis form, e.g. doctor.

This permits faithful display alongside normalized downstream matching. They do not store the same information.

10.6 Debugging with tokenizer.explain

text = "Let's go!"
explanation = nlp.tokenizer.explain(text)

for rule, token_text in explanation:
    print(token_text, "\t", rule)

nlp.tokenizer.explain(text) returns tuples describing the rule/pattern responsible for each resulting token. Use it to diagnose why a contraction, prefix, suffix, infix, exception, or punctuation mark was treated in a particular way.

11. Sentence segmentation

11.1 Accessing sentences

doc = nlp(
    "This is the first sentence. "
    "This is the second sentence. "
    "This is the third sentence."
)

for sent in doc.sents:
    print(sent.text)

Each item from doc.sents is a Span; boundaries are stored in the Doc.

11.2 Why segmentation is difficult

Determining sentence boundaries is not merely splitting at every period. Periods may occur in abbreviations, decimals, citations, and domain expressions. spaCy commonly uses the dependency parser for sentence segmentation, allowing syntax to inform boundaries. This was presented as a sophisticated, generally accurate approach.

Accuracy can decline on specialized genres, conversational data, or social-media text. When parsing is unnecessary or unavailable, a Sentencizer can implement rule-based boundaries without the dependency parser.

Applications include summarization, translation, sentiment-by-sentence, document indexing, and long-text processing.

12. Lemmatization and stemming

12.1 Lemma and lemmatization

A lemma is the dictionary/base form of a token. Lemmatization reduces inflected forms to their lemmas:

eating → eat
eats   → eat
worked → work
playing / played / plays → play

Example:

doc = nlp("I went there for working and worked for 3 years.")
for token in doc:
    print(token.text, token.lemma_)

Benefits:

  • groups inflectional variants;
  • reduces vocabulary variation;
  • improves feature consistency and generalization;
  • useful in information retrieval, semantic analysis, and sentiment analysis.

12.2 Pronoun caveat

The lecture demonstrated a spaCy output/version in which personal-pronoun lemmas such as I, you, me, him, and his were represented by a special PRON/-PRON- lemma to group them semantically. Exact outputs depend on spaCy/model version; current models may preserve lowercase pronoun forms. For the exam, remember the conceptual point: models may use special normalized representations for pronouns.

12.3 Lemmatization versus stemming

Both reduce word variation toward a base/root. Lemmatization aims for a linguistically valid dictionary form; stemming often applies crude affix-stripping rules and may produce a nonword. The live session introduced the distinction but did not develop stemming algorithms in detail.

Lemmatization adds a normalized annotation; it does not overwrite token.text.

13. Named entities and document annotations

for ent in doc.ents:
    print(ent.text, ent.label_)

for sent in doc.sents:
    print(sent.text)

Typical entity types include person, organization, product, location/geopolitical entity, money, date, and time. A trained NER model automatically detects many general entities; a custom component or EntityRuler is required only when generic coverage is inadequate.

Generic pretrained models learn from mixed-domain data. They may fail on specialized categories such as diseases, symptoms, medications, treatments, legal citations, or industry product codes. Fine-tuning or targeted rules supply the missing domain knowledge.

14. Byte Pair Encoding and multilingual tokenization

14.1 BPE

Byte Pair Encoding (BPE) is a subword-learning algorithm:

  1. begin with a small inventory such as characters;
  2. count adjacent symbol pairs;
  3. merge the most frequent pair;
  4. repeat, gradually learning frequent subword units.

Illustration:

l o w → lo w → low

BPE helps split an unseen form such as playfulness into known pieces such as play + fulness, whereas a word tokenizer might return an unknown token.

14.2 Whitespace caveat

If training first splits text by whitespace and then applies BPE, the tokenizer inherits a whitespace assumption. That works reasonably for English but is harmful as a universal multilingual strategy because Chinese, Japanese, Thai, and other languages may omit or inconsistently use spaces.

Desired language-agnostic idea:

Raw text → subword learning/tokenization → subword units

rather than making whitespace a compulsory universal word boundary. The important principle is to align pre-tokenization with the target scripts and languages.

15. Features and limitations of spaCy tokenization

15.1 Key strengths

  1. Speed and efficiency: handles large volumes quickly without necessarily sacrificing general accuracy.
  2. Punctuation awareness: goes beyond naive whitespace splitting and treats punctuation in linguistically useful ways.
  3. Language-specific behavior: tokenization defaults can reflect the chosen language’s conventions.
  4. Customizability: developers can add special cases and rule-based behavior, or train/customize other components such as NER.
  5. Pipeline integration: token boundaries directly support tagging, parsing, NER, and later tasks.

15.2 Limitations

  1. Memory consumption: pretrained packages—especially larger ones—and large documents may require significant RAM, making memory-constrained deployment difficult.
  2. Dependence on pretrained models: models are powerful but generic; specialized domains often require fine-tuning or custom rules/data.
  3. Uneven language support: resource-rich languages such as English tend to have stronger pipelines. Low-resource languages may lack robust pretrained models or complete components. The lecture specifically mentioned possible difficulty for Hindi, Kannada, Telugu, and Malayalam relative to English.
  4. Genre sensitivity: conversations, social media, and highly specialized documents can reduce default sentence/token boundary accuracy.
  5. Customization cost: more rules/components can raise latency, complexity, regression risk, and long-term maintenance.

16. Real-world case studies from the lecture

16.1 Acme Brands — social-media sentiment

Background: Acme Brands, a social-media marketing agency, analyzes conversations to understand sentiment toward client products.

Problem: its system splits on whitespace (spaces/tabs), causing inaccurate sentence segmentation.

Consequences:

  • sentences are broken incorrectly or in half;
  • sentiment is misinterpreted;
  • emojis and hashtags are incorrectly attached/handled and skew analysis.

Suggested solution: rule-based sentence tokenizer

  1. preprocess data appropriately;
  2. use regular expressions to identify sentence-ending patterns;
  3. handle edge cases such as emojis, hashtags, abbreviations, and unconventional punctuation;
  4. test on a held-out/hand-annotated dataset;
  5. compare with the whitespace baseline.

Practical extension: score boundary precision, recall, and F1, then measure whether better boundaries improve sentiment accuracy. Do not delete emojis indiscriminately; an emoji may itself carry sentiment.

16.2 Chatty Corporation — chatbot intent understanding

Background: Chatty Corporation develops customer-service chatbots.

Problem: whitespace tokenization struggles with multi-sentence and compound customer messages, obscuring intent.

Suggested solution: rule-based sentence tokenization combined with POS tagging.

  1. convert text to lowercase and remove irrelevant special characters;
  2. use regex rules for conventional sentence endings;
  3. assign grammatical functions using a pretrained POS tagger;
  4. refine sentence splitting with POS information;
  5. test on customer messages annotated with dialogue acts.

Caveat: lowercasing and special-character removal were the case-study proposal, not universal laws. Preserve casing or symbols if they distinguish products, urgency, order IDs, or intent.

16.3 Lex Machina — legal-document classification

Background: Lex Machina is a legal research and analytics firm that classifies documents by subject matter.

Problem: whitespace tokenization mishandles contracted terms and legal citations.

Suggested solution: hybrid rule- and dictionary-based tokenizer

  1. lowercase where appropriate and remove irrelevant special characters, preserving citation-relevant ones;
  2. use whitespace splitting only as an initial baseline;
  3. identify/join or appropriately decompose contractions using a legal contraction dictionary;
  4. recognize legal citation formats with regex and treat them as coherent units;
  5. apply additional rules for legal abbreviations and edge cases.

The transcript’s spoken “don’t becomes don’t” is evidently a transcription error; the substantive lesson is to recognize contracted forms as intended rather than blindly splitting at punctuation.

17. LinguaTech case study — architecture and trade-offs

17.1 Scenario

LinguaTech builds product-review sentiment tools. Mia explores spaCy annotations:

import spacy

nlp = spacy.load("en_core_web_md")
doc = nlp("SpaCy is an excellent NLP library.")

for token in doc:
    print(token.text, token.pos_, token.dep_)

She can also inspect lemma_, is_stop, entities through doc.ents, and sentences through doc.sents. The case emphasizes that the Doc centralizes all results and references strings efficiently through the shared vocabulary.

17.2 Three design options

  1. Default general pipeline: POS, dependency parse, NER, etc. - strengths: optimized, tested, stable, maintainable, high throughput; - weakness: generic models may miss industry-specific concepts.

  2. Custom pipeline component: refine entity matching or add business/domain annotations. - strengths: domain-specific intelligence, richer entity or contextual recognition; - costs: runs on every document, adds latency, lowers throughput, and increases testing and maintenance.

  3. Post-annotation filtering with is_stop and lemma_: remove selected stop words and use lemmas to reduce variation. - strengths: cleaner, smaller feature space; - weakness: cannot create new domain knowledge and may remove meaningful words such as not.

17.3 Performance concepts

  • Throughput: documents processed per unit time, e.g. 1,000 reviews/second.
  • Latency: time needed to process one document.
  • More enabled work per document normally increases latency and reduces throughput.
  • Maintainability: ease of testing, debugging, updating, adapting to new spaCy versions, and responding to new business requirements.
  • Scalability: ability to handle growing data volume and deployment load with acceptable resources.

17.4 Correct decision

If the explicit priority is maximum throughput on limited hardware, prefer the default/leanest pipeline that still supplies required annotations, and disable unnecessary components where appropriate. This is usually faster and easier to maintain.

If domain-specific accuracy is more valuable, add a custom component only after measuring that its improvement justifies latency and maintenance. Pre-filtering may clean features but is not a substitute for domain recognition.

There is no single best architecture. Balance:

  • general accuracy;
  • domain accuracy;
  • throughput;
  • latency;
  • memory;
  • maintainability;
  • scalability;
  • testing cost.

17.5 Dependency parsing as business value

Dependency relations are not merely grammar exercises. They enable aspect-based sentiment, relation extraction, and domain reasoning by linking an opinion to the correct product feature. A custom component can read these existing relations to determine which adjective modifies an entity or which verb refers to it.

18. Common misconceptions and corrections

  1. “There is one best tokenizer.” No—choice depends on task, language, data, and resource constraints.
  2. “Humans read words, so word tokenization is always best.” Word tokenizers struggle with unseen words, rich morphology, noise, and multilingual text.
  3. “Whitespace splitting is language independent.” It fails on punctuation-rich text and languages without reliable spaces.
  4. “Lowercase, strip punctuation, and remove stop words every time.” These may destroy entity, sentiment, citation, or intent information.
  5. “spacy.blank('en') includes a trained tagger/parser/NER.” It supplies a tokenizer and language defaults, not trained annotations.
  6. “Call nlp() once per word.” Process the contextual text once and reuse its Doc.
  7. “Write tokenizer rules immediately.” Analyze representative data, define expected tokens, and build regression tests first.
  8. “ORTH and NORM are identical.” ORTH preserves the original form; NORM standardizes it.
  9. “The Doc repeats every string.” Tokens reference shared Vocab/StringStore entries using hashes.
  10. “Reading pos_ or dep_ triggers fresh processing.” Those values were computed when the pipeline created the Doc.
  11. “NER always needs handwritten rules.” A trained model detects general entities; custom rules/components extend it for domain cases.
  12. “Pre-filtering and custom components do the same thing.” Filtering reduces/normalizes existing information; a component can add new information.
  13. “A custom component always improves the system.” It may improve domain accuracy but can hurt speed, simplicity, and maintainability.
  14. “The fastest system is automatically best.” Business value may require accuracy or contextual interpretation that justifies extra cost.
  15. “Sentence boundaries are separate from the Doc.” They are annotations accessed through doc.sents.
  16. “Dependency parsing is only for grammar.” It enables contextual sentiment, relation extraction, and feature–opinion linking.

19. Exam-focused comparisons

19.1 Token, lexeme, span, Doc, and Vocab

Term Contextual? Represents Key point
Token Yes One occurrence in a Doc Has POS, dependency, lemma, etc.
Lexeme No Vocabulary word type No sentence-dependent POS/dependency.
Span Yes Slice of a Doc Used for sentences and entities.
Doc Yes Whole processed text Owns tokens and annotations.
Vocab Shared Language vocabulary/string store Avoids duplicate linguistic data.

19.2 Pipeline choices

Choice Best when Benefit Main cost/risk
Blank pipeline Tokenization only or building from scratch Lightweight No trained POS/parser/NER.
Default trained pipeline General NLP and maintainability Strong out-of-box annotations Generic domain knowledge; model memory.
Custom tokenizer rule Stable, known boundary exception Precise handling Regression risk and rule maintenance.
Custom component New domain annotations/business logic Domain accuracy Latency, complexity, testing.
Lemma/stop-word filtering Feature simplification Reduced variation/noise May discard meaning; adds no new knowledge.

19.3 Rule-based, statistical, and hybrid approaches

  • Rule based: transparent and precise for known formats; brittle on unseen variation.
  • Statistical/pretrained: adaptable and contextual; depends on training data and may miss niche formats.
  • Hybrid: combines model context with exact rules/dictionaries; often best for legal, medical, or financial cases, but increases engineering complexity.

20. Likely exam questions and model-answer points

Q1. Define a language-processing pipeline.

An ordered sequence of NLP components in which each processes the same Doc, adds or modifies annotations, and passes it onward. In spaCy, raw text is tokenized first, then components such as the tagger, parser, lemmatizer, and NER run according to the loaded model.

Q2. Why is tokenization foundational?

It decides the atomic units seen by every later stage and therefore affects vocabulary, OOV behavior, feature extraction, embeddings, POS tagging, parsing, NER, memory, sequence length, and model accuracy.

Q3. Distinguish word, subword, and character tokenization.

Word tokenization is interpretable and produces short sequences but has a large vocabulary/OOV problem. Subword tokenization balances vocabulary and coverage and is common in Transformers. Character tokenization virtually removes OOVs and handles misspellings but produces very long, semantically weak sequences.

Q4. Why does spaCy use Doc and Vocab?

Doc holds the contextual token sequence and annotations. Vocab centralizes strings and lexical attributes so repeated strings need not be stored separately, improving memory and lookup efficiency.

Q5. How do you customize and debug a tokenizer?

Collect representative examples, define expected outputs, create tests, add exact special cases with nlp.tokenizer.add_special_case, apply specific rules before broad ones, and inspect behavior with nlp.tokenizer.explain(text).

Q6. Why is sentence segmentation harder than splitting on periods?

Periods occur in abbreviations, decimals, citations, and other non-boundary contexts. spaCy can use syntactic/dependency information; a rule-based Sentencizer is an alternative when parsing is unavailable.

Q7. Explain the spaCy customization trade-off.

Custom rules/components may improve domain accuracy and entity coverage but add latency, memory/computation, regression testing, code complexity, and maintenance. Choose them based on measured business benefit.

Q8. Why can whitespace pre-tokenization harm multilingual BPE?

It assumes spaces mark words, which is not true for many scripts/languages. This restricts BPE’s language independence and can yield poor segmentation for Chinese, Japanese, Thai, and similar cases.

Q9. Compare lemmatization and stop-word filtering.

Lemmatization normalizes inflected words to dictionary forms; stop-word filtering removes selected common function words. Both may reduce feature complexity, but filtering can delete crucial meaning (especially negation), and neither substitutes for a domain-aware component.

Q10. Recommend an architecture for LinguaTech.

For highest throughput on limited hardware, use the default or lean required pipeline and avoid unnecessary custom work. If measured domain accuracy is insufficient, add a targeted custom component and accept/test the latency-maintenance trade-off. Use lemma/stop-word filtering only when validated for the sentiment task.

21. Final rapid-revision checklist

  • spaCy is open-source, fast, production-oriented, and pretrained-model based.
  • spacy.load() returns the Language pipeline; nlp(text) returns a Doc.
  • Load the appropriate model size and language; model capabilities determine annotations.
  • Tokenization creates meaningful atomic units and occurs before most downstream analysis.
  • Each component has a defined role and passes the annotated Doc onward.
  • Doc and Vocab are backbone data structures; Token, Span, and Lexeme have distinct meanings.
  • Shared integer-hash string storage improves memory efficiency.
  • spacy.blank() does not supply trained tagger/parser/NER components.
  • Use doc.sents for sentences and doc.ents for named entities.
  • Lemmas are base forms; exact pronoun normalization can vary by model/version.
  • Naive whitespace or period splitting is not robust.
  • Tokenizer strategy must match task, language, noise, and resources.
  • Special cases can override default punctuation behavior.
  • ORTH is original surface text; NORM is normalized text.
  • tokenizer.explain() reveals which rule created each token.
  • Create representative expected-output tests before adding rules.
  • BPE merges frequent adjacent units and reduces OOVs.
  • Do not assume whitespace is universal in multilingual NLP.
  • spaCy strengths: speed, punctuation handling, language-specific defaults, customization, pipeline integration.
  • spaCy limits: RAM use, generic pretrained knowledge, uneven low-resource-language support, genre sensitivity, and customization cost.
  • The correct production design balances accuracy, latency, throughput, memory, scalability, and maintainability.

Review-Week Augmentation

The review reinforces that tokenization is not a neutral preliminary step: it determines what token rules can see. A Matcher sequence such as [{"IS_DIGIT": True}, {"IS_ALPHA": True}] requires adjacent numeric and alphabetic tokens. Punctuation in 3:30 pm or 10-12 people may introduce intervening tokens, so inspect the Doc token-by-token before changing a failing pattern.

Preprocessing must also be task-aware. Normalization can unify REFUND, Refund, and refund; lemmatization can unify returned, returning, and returns under return. However, indiscriminate stop-word removal is dangerous: removing not from “I have not received my package” destroys the distinction from “I have received my package.” More preprocessing is not automatically better; preserve information that changes intent.
