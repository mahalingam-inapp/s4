1. Week overview

Week 4 connects two complementary approaches to language understanding:

  1. Rule-based/token-based matching: explicitly describe the token sequence or linguistic properties that constitute a match.
  2. Vector-based semantics: represent words, spans, sentences, products, users, tickets, or agents numerically and compare meanings rather than exact wording.

The central practical lesson is that neither approach is universally sufficient. Exact rules are excellent for well-defined structures such as greetings, account identifiers, or domain keywords. Vectors are better when users express the same intent with different words. Production systems commonly combine both in a hybrid score or decision pipeline.

2. Regular expressions and why token matching is useful

2.1 Regular expressions

A regular expression (regex) is a sequence of characters specifying a search pattern; it denotes a set of strings that follow that pattern. A regex may contain ordinary letters and digits plus metacharacters with special meanings. Python’s built-in re library supports regular expressions; a separate third-party regex library provides extended support and has been positioned as a possible successor.

Example idea from the lecture:

r"Barack\s(Hussein\s)?Obama"
  • \s matches whitespace, including spaces, tabs, and line breaks.
  • (Hussein\s)? makes the middle-name segment optional.
  • ? means zero or one occurrence.
  • Consequently, the pattern can match both Barack Obama and Barack Hussein Obama despite variations in whitespace.

Regex is powerful for character-level structures, but even short expressions can be difficult to read, debug, and maintain. They are especially error-prone around whitespace, punctuation, and numbers. This is why NLP production systems often prefer a token-aware matcher when the rule naturally concerns words and their linguistic attributes.

2.2 spaCy’s Matcher

spaCy’s Matcher is a rule-matching engine operating on sequences of tokens in Doc and Span objects. Rules may refer to token text or linguistic annotations, making them more readable and maintainable than equivalent character-level regexes.

Important properties:

  • A pattern is a list of dictionaries.
  • Each dictionary describes one token.
  • A pattern always describes a continuous sequence of tokens.
  • The Matcher must be initialized with the same vocabulary used by the documents it processes.
  • A rule can have one or more alternative patterns.
  • Rules can invoke custom callbacks, merge spans, assign labels, and associate entity IDs for basic linking/disambiguation.
  • For a large fixed terminology list, use PhraseMatcher, which accepts Doc objects as patterns and is more appropriate than writing many token rules.

3. Building matcher rules in spaCy

3.1 Basic greeting example

import spacy
from spacy.matcher import Matcher

nlp = spacy.load("en_core_web_md")
doc = nlp("Good morning. I want to reserve a ticket.")

matcher = Matcher(nlp.vocab)
pattern = [
    {"LOWER": "good"},
    {"LOWER": "morning"},
    {"IS_PUNCT": True},
]
matcher.add("MORNING_GREETING", [pattern])

matches = matcher(doc)
for match_id, start, end in matches:
    span = doc[start:end]
    rule_name = nlp.vocab.strings[match_id]
    print(rule_name, start, end, span.text)

Conceptual reading of the pattern:

  1. a token whose lowercase form is good;
  2. followed by a token whose lowercase form is morning;
  3. followed by a punctuation token.

The result of matcher(doc) is a list of triples:

(match_id, start, end)
  • match_id is an integer identifier stored in spaCy’s string store.
  • Recover its name with nlp.vocab.strings[match_id].
  • start is the first matched token index.
  • end is exclusive, exactly like Python slicing, so the match is doc[start:end].

Whitespace between words does not need to be represented as a matcher token. One or even two spaces between Good and morning do not change the token rule, because the matcher compares tokens and token attributes rather than literal inter-word characters.

Version caveat: older spaCy examples used matcher.add(name, None, pattern). Current spaCy uses matcher.add(name, [pattern]). The lecture encountered and corrected this API-version difference.

3.2 Multiple named patterns

morning = [
    {"LOWER": "good"}, {"LOWER": "morning"}, {"IS_PUNCT": True}
]
evening = [
    {"LOWER": "good"}, {"LOWER": "evening"}, {"IS_PUNCT": True}
]

matcher.add("MORNING_GREETING", [morning])
matcher.add("EVENING_GREETING", [evening])

Applied to Good morning. ... Good evening!, the match list contains two items with distinct rule IDs. Patterns may differ by only one token, but can still be registered independently when separate downstream behavior is required.

If both alternatives should trigger the same behavior, add both under one ID:

matcher.add("GREETING", [morning, evening])

3.3 Common token attributes

Attribute Meaning Example use
LOWER Lowercased token text case-insensitive hello, HELLO, Hello
TEXT / ORTH Exact token text distinguish Bill from bill
LENGTH Token length find all one-character tokens
IS_PUNCT Whether token is punctuation require !, ., ?, etc.
IS_DIGIT Whether token is numeric amounts, dates, identifiers
IS_ALPHA Whether token consists of alphabetic characters require a word token
SHAPE Abstract character pattern match forms such as two letters followed by two digits
LEMMA Base form match book, books, booked through a lemma rule
POS, TAG, DEP Part of speech, detailed tag, dependency label linguistic rules rather than literal words
REGEX under TEXT Regex constrained to one token’s text digit blocks within token-aware patterns
OP Quantifier for a token pattern optional/repeated token specifications

Matcher quantifiers mirror familiar regex ideas:

  • "?": zero or one
  • "*": zero or more
  • "+": one or more
  • "!": must not occur at this position

3.4 Digit-plus-word example and tokenizer caveat

pattern = [
    {"IS_DIGIT": True},
    {"IS_ALPHA": True},
]

This can match two apples if spaCy marks two as digit-like and apples as alphabetic. It will not necessarily match the intended part of 2 o'clock, because tokenization and the apostrophe mean the second token is not a plain alphabetic token. The general lesson is critical:

Matcher correctness depends on spaCy’s token boundaries and annotations. Always inspect tokens before diagnosing a failed rule.

3.5 Combining matcher rules with token-level regex: IBAN example

An IBAN (International Bank Account Number) is an international account-number format. The lecture’s simplified pattern begins with two capital letters and two digits, followed by one or more numeric blocks. Examples included UK- and France-style identifiers such as GB98 ... and FR76 ....

iban_pattern = [
    {"SHAPE": "XXdd"},
    {"TEXT": {"REGEX": r"\d{1,4}"}, "OP": "+"},
]

matcher.add("IBAN", [iban_pattern])
  • SHAPE: "XXdd" expresses two uppercase letters followed by two digits.
  • r"\d{1,4}" means a token consisting of one to four digits.
  • OP: "+" requires one or more such numeric blocks.

This illustrates a useful hybrid: the overall structure is token-based, while regex checks the characters within particular tokens. In a real financial application, validation should additionally enforce official country-specific IBAN lengths and checksum rules; matching shape alone detects candidates, not guaranteed-valid accounts.

3.6 hello [punctuation] world and alternatives

with_punct = [
    {"LOWER": "hello"},
    {"IS_PUNCT": True},
    {"LOWER": "world"},
]
without_punct = [
    {"LOWER": "hello"},
    {"LOWER": "world"},
]
matcher.add("HELLO_WORLD", [with_punct, without_punct])

This matches case variants and optionally supports the punctuation-free form by registering two alternatives. By default, matching only returns spans; it does not mutate the document. To merge matches or assign entities, pass an on_match callback to add and implement that behavior explicitly.

3.7 Matcher versus regex versus PhraseMatcher

Tool Best level Strength Limitation / risk
Regex Characters Precise raw-text formats readability and punctuation/spacing complexity
Matcher Tokens + annotations maintainable linguistic rules, callbacks depends on tokenization and pipeline annotations
PhraseMatcher Large phrase lists efficient terminology lookup less expressive for arbitrary linguistic constraints

Practical uses include greetings, product attributes, order IDs, bank identifiers, clinical terms, skill names, intent cues, and structured phrases in contracts.

4. From symbolic word identity to word vectors

4.1 Why text needs numerical representation

Machine-learning algorithms require numerical input. A simple representation assigns every vocabulary item an index and encodes it as a one-hot vector: all components are zero except the component corresponding to that word.

If vocabulary size is V, each word vector has length V. A sentence of N words becomes an N × V matrix, one row per word. For example, I want a pizza becomes four one-hot rows.

4.2 Limitations of one-hot encoding

  • Sparse: almost all entries are zero.
  • High-dimensional: dimension equals vocabulary size.
  • Memory-heavy for large vocabularies.
  • No semantic geometry: cat is no closer to dog than to aircraft.
  • No learned relation between synonyms or concepts.
  • Vocabulary growth changes the representation size and produces an OOV problem.

4.3 Word embeddings / word vectors

A word vector is a fixed-size, dense, real-valued learned representation of a word. Semantically related words occupy nearby regions in vector space. Word vectors encode aspects of word meaning, hence the phrase distributed semantics: information about meaning is distributed over many dimensions rather than assigned to one explicit vocabulary coordinate.

The underlying distributional hypothesis is that words appearing in similar contexts tend to have similar meanings. For example, cat, dog, and tiger occur in animal-related contexts; pizza, burger, and salad occur in food contexts. Training on large corpora learns such relationships without a hand-written synonym list.

Word embeddings support:

  • word/sentence semantic similarity;
  • text classification;
  • named-entity recognition (people, organizations, locations, etc.);
  • semantic search and retrieval;
  • intent recognition;
  • clustering and visualization;
  • recommendations;
  • ticket routing and knowledge-base retrieval.

5. spaCy pre-trained vectors

5.1 Models and model choice

spaCy offers language pipelines of different sizes, conventionally including:

  • en_core_web_sm — small English pipeline;
  • en_core_web_md — medium English pipeline with static vectors;
  • en_core_web_lg — large English pipeline with broader vector vocabulary.

The lecture cited approximately 300-dimensional vectors, about 20,000 vocabulary words for the medium model, and about 685,000 for the large model. Treat exact package statistics as model-version-dependent. spaCy also supports pipelines for other languages, including German and Spanish.

Larger vector vocabularies improve coverage but require more disk space and memory. The lecture recommends the medium model as a practical default when text scale/coverage requirements are uncertain. A small pipeline may expose a vector-shaped representation from internal features, but for meaningful static lexical similarity one should verify that the installed pipeline actually contains word vectors.

import spacy
nlp = spacy.load("en_core_web_md")

If loading fails, install/download the relevant model in the target environment. Legacy generic model names may be deprecated; use explicit package names such as en_core_web_md.

5.2 Accessing vectors

doc = nlp("I ate a banana.")
banana = doc[3]

banana.vector          # NumPy ndarray
type(banana.vector)    # numpy.ndarray
banana.vector.shape    # commonly (300,) for md/lg static vectors

Token.vector provides the word vector. Doc.vector and Span.vector are also available; in the static-vector setup discussed in class, a document/span vector is formed by averaging constituent token vectors.

doc.vector
doc[1:4].vector

Mean pooling is simple and fast but loses word order, syntactic structure, and some contextual nuance. Stop words can also dominate an unweighted average, so preprocessing or weighted pooling may help task-specific systems.

5.3 Vocabulary coverage and OOV words

Words without a vector in the model are out of vocabulary (OOV).

for token in nlp("you went there afskfsd"):
    print(token.text, token.is_oov, token.has_vector)
  • token.is_oov asks whether the token is absent from the vector vocabulary.
  • token.has_vector asks whether it has a usable vector.

An OOV-based low similarity score does not prove that two words are semantically unrelated; it may simply indicate missing representations. Domain jargon, novel product codes, names, abbreviations, and misspellings are common OOV sources.

5.4 Quality considerations

  • Vector dimension controls representation capacity and computational/memory cost.
  • Training-data quality and diversity influence learned biases, vocabulary coverage, and downstream accuracy.
  • Generic pre-trained vectors transfer broad semantic knowledge, especially useful when labeled data is scarce.
  • A specialized task may benefit from fine-tuning or domain-specific embeddings.
  • Static vectors assign one vector per word form, so polysemous words such as bank may conflate meanings. Contextual models address this better.
  • Similar words are useful for retrieval but can be harmful when a task must separate fine-grained classes that appear in similar contexts.

6. Semantic similarity

6.1 Why semantic similarity matters

Natural language expresses one concept in many forms. Every language contains synonyms and semantically related words. An intent such as booking can appear as book, reserve, make a reservation, or buy; travel arrival may be expressed with land, arrive, or fly to, while departure may use leave, depart, or fly from.

Chatbot and intent-classification platforms therefore request many utterance examples per intent: examples train the classifier to recognize varied phrasing. The lecture distinguishes two routes to semantic recognition:

  1. domain synonym dictionaries;
  2. word-vector-based semantic similarity.

6.2 Domain synonym sets

A synset means synonym set. Domain lists may mix general synonyms and domain-specific equivalences:

verb_synsets = [
    ["show", "list"],
    ["book", "make a reservation", "buy", "reserve"],
]
object_synsets = [
    ["meal", "food"],
    ["aircraft", "airplane", "plane"],
]

One way to compare intent-bearing utterances is:

  1. parse both sentences;
  2. identify the transitive verb and direct object;
  3. compare their lemmas against relevant synsets;
  4. treat the utterances as the same intent only if the required semantic roles are compatible.

For Show me all aircrafts that CP uses versus List all meals on my flight, the verbs show and list share a synset, but aircraft and meal do not. Therefore the complete intents differ.

Dependency-based extraction illustrated in the lecture:

def verb_and_object(doc):
    for token in doc:
        if token.dep_ == "dobj":  # label/version can vary
            return token.head.lemma_, token.lemma_
    return None, None

The lecturer corrected coding slips in list comprehensions: the same loop variable must be used consistently, e.g. [syn for syn in verb_synsets if verb in syn]; undefined names such as item, v2, or misspelled variables cause errors.

Advantages of synonym lists

  • transparent and controllable;
  • excellent for small, stable, domain-specific vocabularies;
  • deterministic and easy to explain.

Limitations

  • extensive manual maintenance;
  • incomplete coverage of paraphrases;
  • repeated dictionary lookup can become inefficient for very large sets;
  • phrases, morphology, context, and polysemy need careful handling;
  • domain meaning can differ from general-language meaning.

6.3 Vector-based similarity in spaCy

spaCy container types—including Token, Span, and Doc—provide .similarity(). Different container types can be compared, such as token-to-doc or doc-to-span, provided they are represented in a compatible embedding space.

doc1 = nlp("I visited England.")
doc2 = nlp("I went to London.")

score = doc1.similarity(doc2)
self_score = doc1.similarity(doc1)  # approximately 1

The first pair receives a relatively high score because of related travel/location semantics. Comparing an object with itself gives 1 (subject to ordinary floating-point behavior).

For the earlier intent example, keep token objects rather than extracting only strings:

def verb_and_object_tokens(doc):
    for token in doc:
        if token.dep_ == "dobj":
            return token.head, token
    return None, None

verb1, obj1 = verb_and_object_tokens(doc1)
verb2, obj2 = verb_and_object_tokens(doc2)
object_similarity = obj1.similarity(obj2)
verb_similarity = verb1.similarity(verb2)

The lecture reported a very low object score (about 0.098) and a low verb score (about 0.23) for its processed example, supporting the conclusion that the utterances do not share an intent. Exact scores vary by model/version. A transcription slip said obj.similarity(verb2) at one point; conceptually, direct objects should be compared with direct objects and verbs with verbs.

6.4 Cosine similarity

The standard similarity measure for embeddings is cosine similarity, which compares direction rather than raw magnitude:

$$ \operatorname{cos}(\mathbf{a},\mathbf{b}) = \frac{\mathbf{a}\cdot\mathbf{b}} {\lVert\mathbf{a}\rVert\,\lVert\mathbf{b}\rVert} $$

  • 1: same direction / maximally similar under the measure.
  • 0: orthogonal / no directional similarity.
  • -1: opposite directions (possible mathematically).

The lecture often describes practical spaCy similarity as ranging from 0 to 1, but cosine mathematically ranges from −1 to 1. Real embedding outputs and library behavior depend on the vectors. Do not interpret a threshold as universal.

Cosine is preferred because vector magnitude may reflect frequency or pooling length, while direction more directly represents the learned semantic profile. Normalizing vectors to unit length makes cosine comparison a dot product and supports efficient nearest-neighbor search.

Critical rule: compare vectors produced by the same model/embedding space. Coordinates from unrelated models have no shared meaning.

6.5 Similarity thresholds

A threshold turns a continuous score into an operational decision:

if score ≥ high threshold: automate
elif score ≥ lower threshold: suggest and request human confirmation
else: send to manual handling / fallback

There is no globally correct threshold. Tune it on validation data according to the cost of false positives and false negatives. High thresholds improve precision but may reduce automation/recall; low thresholds increase coverage but risk incorrect matches.

7. Visualizing word-vector structure with PCA

Vectors in the lecture are 300-dimensional, so they cannot be plotted directly. Principal Component Analysis (PCA) projects them into two dimensions for visualization.

import numpy as np
import matplotlib.pyplot as plt
from sklearn.decomposition import PCA

vocab = nlp(
    "cat dog tiger elephant bird monkey lion cheetah "
    "burger pizza food cheese wine salad noodles macaroni fruit vegetable"
)

tokens = [t for t in vocab if t.has_vector]
words = [t.text for t in tokens]
vectors = np.vstack([t.vector for t in tokens])
xy = PCA(n_components=2).fit_transform(vectors)

plt.scatter(xy[:, 0], xy[:, 1])
for word, (x, y) in zip(words, xy):
    plt.text(x, y, word, fontsize=15)
plt.show()

Procedure:

  1. load spaCy and the medium vector model;
  2. create a document containing animal and food vocabulary;
  3. retain tokens with vectors;
  4. vertically stack vectors into a matrix with np.vstack;
  5. fit PCA with two components and transform the matrix;
  6. scatter-plot coordinates and annotate each word.

The plot formed two broad semantic groups: animals and food. Animal words were relatively close and uniformly distributed, while food words showed subgroups within the larger class. This demonstrates that learned vector geometry reflects semantics.

Caveat: PCA is a lossy linear projection. A visually close or distant pair in 2-D need not preserve its exact high-dimensional relation. Use the plot for exploration, not as proof of model quality.

8. Practical semantic-search and recommendation pipeline

8.1 General pipeline

Raw query/item text
  → tokenize and normalize
  → apply exact/domain matcher rules
  → generate token/document embeddings
  → compare with cosine similarity
  → combine exact and semantic scores
  → rank candidates
  → apply confidence threshold / human fallback
  → monitor outcomes and improve

Possible hybrid score:

$$ S = \alpha S_{token} + \beta S_{semantic} + \gamma S_{business} $$

where token match captures exact evidence, semantic score captures paraphrase/meaning, and business score can encode availability, popularity, agent workload, or other operational constraints. Coefficients must be tuned empirically rather than assumed.

8.2 Phrase-aware processing

Meaning may be carried by multiword phrases such as make a reservation, credit card, order status, or first contact resolution. Token-by-token synonym replacement can destroy these units. Use PhraseMatcher, noun chunks, entity spans, or explicit phrase rules before pooling/vector comparison.

8.3 Query expansion

Expand a user query with controlled synonyms, spelling variants, categories, or semantically nearby terms. This helps short or ambiguous queries retrieve candidates that exact token matching misses. Expansion must be domain constrained to avoid semantic drift.

9. Case studies from the lectures

9.1 E-commerce product discovery and recommendation

Situation: A platform has a huge catalog of product descriptions, categories, attributes, and sometimes images. Descriptions vary in length and quality; user queries are short and ambiguous. Existing recommendations rely mainly on purchase history and neglect product content.

Objective: identify relevant products through exact keyword evidence plus semantic similarity, improve product discovery, personalize recommendations, and increase satisfaction and sales.

Solution

  1. Tokenize and normalize query/catalog text.
  2. Match important product tokens and attribute phrases (brand, category, color, size, material).
  3. Generate embeddings for products and queries.
  4. Compute semantic similarity.
  5. Combine exact-match and semantic scores.
  6. Rank search results or generate recommendations.
  7. Expand queries with synonyms/related phrases.
  8. Optionally incorporate user embeddings from preferences or interaction history.
  9. Continuously evaluate and personalize.

The fashion-retail variant also includes visual search, connecting image-derived signals with textual descriptions and user preferences.

Metrics

  • click-through rate (CTR);
  • conversion rate;
  • average order value;
  • average session duration;
  • no-result rate;
  • product discovery/engagement;
  • user satisfaction.

Use case: comfortable footwear for running should retrieve lightweight jogging shoes even without exact word overlap, while token rules can preserve hard constraints such as size 9, color blue, or brand.

9.2 Search relevance with spaCy vectors

Problem: low search relevance produces dissatisfaction.

Workflow

  1. collect product descriptions, categories, and search queries;
  2. clean and process text;
  3. convert descriptions and queries to vectors;
  4. compute query-product cosine similarities;
  5. rank products by score;
  6. monitor results and adjust vectorization and similarity logic.

Challenges and remedies

  • Vectorizing a very large catalog is computationally expensive: precompute catalog vectors, batch processing, index them with approximate nearest-neighbor search, and consider dimensionality reduction where justified.
  • Poor/divergent training data reduces vector quality: improve data quality and use domain-representative embeddings.
  • Static vectors may not capture full document context: introduce phrase-aware or contextual representations and re-ranking.
  • Generic similarity can ignore hard filters: combine semantic retrieval with token/metadata constraints.

9.3 Customer-support ticket routing

Situation: high volumes of diverse inquiries require accurate categorization, prioritization, and assignment to agents. The goal is lower handling time, higher first-contact resolution (FCR), and better customer/agent satisfaction.

Data

  • historical customer tickets and resolutions;
  • agent profiles and demonstrated expertise;
  • knowledge-base (KB) articles;
  • categories, priorities, outcomes, and feedback.

Vector-based solution

  1. preprocess tickets, profiles, and KB articles: lowercase as appropriate, handle punctuation/stop words carefully, normalize text;
  2. obtain word vectors;
  3. aggregate them into document embeddings;
  4. create each agent’s expertise representation from profile/history;
  5. embed KB articles in the same space;
  6. calculate ticket-agent and ticket-article cosine similarity;
  7. route to the best qualified agent and retrieve the most relevant KB article;
  8. apply confidence thresholds and human override;
  9. feed confirmed decisions and outcomes back into evaluation.

Semantic routing outperforms literal keywords when money back, return payment, and refund express the same intent. It can also reveal clusters of recurring inquiries, gaps in KB coverage, and how agent expertise evolves.

Business benefits

  • reduced handling time;
  • better FCR;
  • improved agent productivity;
  • improved customer and agent satisfaction;
  • better use and discovery of KB content;
  • operational insight from semantic clusters.

9.4 ShopEase-style deployment strategy (review augmentation)

The review case expands support routing into a deployment and governance problem.

Alternatives

  • Full rollout: maximum immediate reach but high operational risk if thresholds or embeddings are wrong.
  • Pilot: limited deployment to selected categories/agents; slower coverage but safer measurement and tuning.
  • Manual override: agents can correct recommendations; improves trust and supplies labeled ground truth.

Best practical strategy: launch a pilot with manual override, use tiered thresholds, monitor KPIs, then expand gradually.

Tiered logic

high confidence → automatic route / answer suggestion
medium confidence → ranked recommendation for agent confirmation
low confidence → manual triage

Manual choices create ground truth for threshold optimization and error analysis. The feedback loop should update agent profiles, identify missing knowledge articles, discover emerging inquiry clusters, and retest performance. Thresholds may differ by category because the cost of an incorrect billing route can differ from an incorrect product-information route.

Evaluation KPIs

  • routing accuracy;
  • precision/recall by issue class;
  • FCR;
  • mean handling and resolution time;
  • escalation/reassignment rate;
  • agent acceptance/override rate;
  • customer satisfaction;
  • coverage at each confidence tier;
  • computational cost and latency.

9.5 Rule-based customer-support chatbot

Common inquiry areas: order status, returns, refund, product information, size, and color.

Operation

  1. identify frequent keywords and phrases;
  2. tokenize each submitted query;
  3. compare tokens/phrases to predefined patterns;
  4. if a match occurs, select and send the corresponding predefined response;
  5. otherwise use fallback/escalation.

Challenges

  • Exact tokens ignore context and can trigger inaccurate responses.
  • Synonyms and polysemy (one word with multiple meanings) are difficult.
  • Short queries are especially ambiguous.

Lecture remedies: expand patterns to include common phrases and idioms, and build a thesaurus mapping synonyms to canonical keywords. A stronger extension is a hybrid semantic fallback plus confidence-aware escalation.

9.6 Word-vector product recommendations

Collaborative filtering may show diminishing accuracy and engagement because it relies on user-item interactions rather than content. Vector-based recommendations add semantic and contextual relations among product descriptions and user preferences.

Steps:

  1. preprocess text;
  2. generate word vectors;
  3. create product embeddings;
  4. create a user vector from the products/descriptions the user prefers;
  5. compare user and product vectors;
  6. recommend the highest-scoring eligible items.

Normalize/average carefully so a user with a long interaction history does not receive a vector whose magnitude dominates merely because of count. Combine semantic relevance with availability, diversity, novelty, business constraints, and purchase-history signals. Expected outcomes are more relevant personalized suggestions, improved engagement and loyalty, higher satisfaction, and increased sales.

10. Common pitfalls and corrections

  1. “Regex and Matcher are the same.” Regex is character-based; Matcher is token/annotation-based.
  2. “Spaces must appear in a matcher pattern.” Whitespace normally separates tokens and is not a token pattern item.
  3. “The end index is included.” It is exclusive: use doc[start:end].
  4. “Matcher modifies the document automatically.” It returns matches; callbacks must implement merging or labeling.
  5. “Any spaCy pipeline provides equally good static vectors.” Verify has_vector, OOV coverage, and pipeline metadata; medium/large vector packages generally provide better lexical coverage.
  6. “All words have vectors.” Domain terms and noise may be OOV.
  7. “A zero similarity proves unrelated meaning.” Missing vectors can also produce a weak score.
  8. “Similarity means identity.” Similar meaning is not the same as being interchangeable in every intent or business rule.
  9. “Cosine is always 0–1.” Its mathematical range is −1 to 1.
  10. “One universal threshold works.” Thresholds depend on the model, domain, class, and error costs.
  11. “Average word vectors understand syntax.” Averaging loses order and structure.
  12. “PCA plot distances are exact.” A 2-D projection discards information.
  13. “Embedding matching replaces exact constraints.” IDs, sizes, dates, negation, legal terms, and required attributes often need explicit rules.
  14. “A synonym dictionary scales without cost.” Coverage and maintenance become difficult; large repeated lookups may be inefficient.
  15. “Token rules work independently of tokenization.” Pattern behavior is determined by token boundaries and annotations.
  16. “High semantic similarity guarantees the same intent.” Compare intent-bearing roles, not only whole-sentence averages; show aircraft and list meals share context but request different objects.

11.1 One-hot vectors versus embeddings

Property One-hot Learned embedding
Dimension vocabulary size V fixed, e.g. 300

11.2 Synsets versus vectors

Property Synonym sets Word vectors
Construction hand-curated learned from corpora

The exam-quality recommendation is usually a hybrid: exact rules create precision and enforce constraints; embeddings add recall and semantic generalization; thresholds and human review manage risk.

12. High-value exam answers

Define token-based matching

Token-based matching is rule-based detection of continuous token sequences where each pattern element specifies token text or annotations such as lowercase form, punctuation status, shape, lemma, POS, dependency, or a token-level regex. spaCy’s Matcher returns (match_id, start, end) triples and can invoke pattern-specific callbacks.

Define a word vector

A word vector is a fixed-size dense real-valued learned representation in which semantic and distributional relationships are encoded geometrically; semantically related words tend to have nearby vectors.

Explain why embeddings improve upon one-hot encoding

One-hot encoding has vocabulary-sized sparse vectors and represents only word identity. Embeddings are compact, dense, and learned from contexts, so they support similarity, transfer, clustering, semantic search, and downstream classification.

Explain semantic similarity methods

Synonym-list methods compare extracted lemmas/roles against manually prepared equivalence classes; they are transparent but hard to scale. Vector methods compare learned representations, commonly through cosine similarity; they generalize to unseen wording but depend on vector quality, shared embedding space, OOV coverage, and suitable thresholds.

Explain cosine similarity

Cosine similarity is the normalized dot product of two vectors. It measures directional alignment independently of magnitude, ranges mathematically from −1 to 1, and is widely used to rank words/documents represented in the same embedding space.

Design a production solution

  1. Frame the measurable business problem.
  2. Inspect text quality, labels, class balance, ambiguity, and vocabulary.
  3. Normalize/tokenize while retaining meaning-bearing phrases and negation.
  4. Apply token rules for exact entities and constraints.
  5. Embed queries and candidates in one shared space.
  6. calculate and combine token, semantic, and business scores.
  7. rank candidates and apply category-sensitive thresholds.
  8. pilot with manual override.
  9. measure task and business KPIs.
  10. use feedback as ground truth for threshold/rule/model improvement.

Review-Week Augmentation

High-yield matcher distinctions from the review:

  • Regex operates on character patterns and is not inherently aware of tokens, lemmas, POS, dependencies, entities, or semantics.
  • spaCy’s Matcher operates on ordered tokens. Use LOWER for case-insensitive matching; TEXT preserves exact surface text, ORTH is orthographic form, and SHAPE captures structural character form.
  • Successive pattern dictionaries normally constrain successive tokens. IS_DIGIT → IS_ALPHA matches 2 apples, not arbitrarily separated number/word pairs, and its result depends on how punctuation is tokenized.

The review contrasts one-hot vectors (sparse, vocabulary-sized, orthogonal even for related words) with dense embeddings (fixed-dimensional semantic representations). The course convention is that en_core_web_md provides 300-dimensional vectors. Cosine similarity is

\[ \cos(\theta)=\frac{A\cdot B}{\|A\|\|B\|}. \]

The material treats roughly 0.6–0.9 as indicative of semantic similarity, but this is a model/domain-dependent guide, not a universal boundary. High similarity means relatedness, not necessarily exact synonymy: doctor and nurse may be close while remaining distinct.
