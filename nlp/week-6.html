1. Week objectives and conceptual map

Week 6 moves from using a pretrained NLP pipeline to preparing data and training it. The stated objectives were:

  1. annotate and prepare data for spaCy models;
  2. update an existing statistical pipeline component, especially NER;
  3. train a new, domain-specific NER component from scratch;
  4. save, reload, test, and visualize the resulting model; and
  5. apply pretrained NER to an airline-review business problem, then distinguish raw NLP output from useful business insight.

The end-to-end logic is:

Raw customer logs/reviews
        ↓
clean and structure the text
        ↓
annotate relevant phenomena (entities, intents, POS, relations, etc.)
        ↓
convert annotations to spaCy training examples
        ↓
train/fine-tune only the required component
        ↓
evaluate on unseen positive and negative examples
        ↓
save and deploy the updated pipeline
        ↓
validate/filter model output before business interpretation

Lecturer emphasis: Preparing good training data is always the first step in model training. The model learns what the examples point it toward; poor or narrow examples produce poor generalization.

2. Data annotation

2.1 Definition

Data annotation is the preparation of labeled training data. It transforms unstructured raw text—customer logs, feedback, reviews, documents, and other noisy text—into examples from which a statistical NLP model can learn.

Annotation can label:

  • named entities and their types;
  • intents;
  • part-of-speech (POS) tags;
  • dependency relationships;
  • relations between entities; and
  • any other target required by the application.

Example conceptual annotation:

{
  "sentence": "I visited JFK Airport",
  "entities": [
    {"value": "JFK Airport", "label": "LOC"}
  ]
}

The labels explicitly tell the statistical algorithm what it should learn. If the objective is entity recognition, the training examples must mark the desired entity spans and labels.

2.2 Why annotation matters

  • Raw text is not a sufficient supervised-learning signal. The model needs the expected output.
  • Marked examples connect inputs to correct outputs.
  • During NER training, the model learns to reproduce marked spans on unseen text.
  • Annotation makes otherwise unstructured customer data machine-consumable.
  • Consistent annotations determine the meaning of every label and therefore the behavior of the finished system.
  • Writing large annotation files manually is slow and error-prone, motivating annotation tools.

2.3 Structure of an NER annotation

For each entity, spaCy-style NER data needs three values:

Field Meaning
start zero-based character index at which the entity begins
end character index immediately after the final entity character
label entity class, e.g. GPE, PERSON, DRUG, DIS

Entity spans are therefore represented as:

(start_character, end_character, "LABEL")

The interval is half-open, [start, end): start is included and end is excluded. This is why the slice text[start:end] should equal the annotated entity text.

Exam trap: Offsets are character positions, not word numbers. Misaligned offsets can cause warnings, ignored entities, or incorrect supervision.

2.4 Training-data format

A small NER training set is a list of (text, annotation_dictionary) pairs:

TRAIN_DATA = [
    ("I will visit you in Munich.",
     {"entities": [(20, 26, "GPE")]}),
    ("I am going to Victoria's house.",
     {"entities": [(14, 22, "PERSON")]}),
    ("I go there.",
     {"entities": []}),
]

The transcript’s live typing contained several offset/label slips; the invariant to remember is:

assert text[start:end] == intended_entity

Each pair contains:

  1. the original sentence; and
  2. a dictionary whose entities value is a list of labeled spans.

If there are no entities, the correct form is:

{"entities": []}

It should not be omitted, written as None, or replaced by malformed brackets.

2.5 Why empty-entity examples are essential

An entity-free sentence is a negative example. It teaches the model that some text contains no target entity.

If training includes only sentences containing entities, the model can overgeneralize and invent entities in ordinary text. Negative examples help it learn when not to predict a span and therefore reduce false positives.

Practical examples:

  • Navigation NER: "Navigate home" is positive if home is a destination; "Navigate" may be negative.
  • Medical NER: "Patients were followed for six months" can be a negative example if the schema contains only DRUG and DIS.
  • Support-ticket NER: "Thanks, the problem is resolved" may contain no product, fault code, or location.

Lecturer emphasis from the live session: Keep such examples. A system exposed only to one kind of labeled sentence may assume every real-world sentence must contain a label.

2.6 Data quality and annotation policy

For reliable learning:

  • define every label precisely;
  • decide whether boundary punctuation and modifiers belong inside a span;
  • use the same policy across annotators;
  • include diverse wording and both positive and negative examples;
  • check character offsets programmatically;
  • resolve ambiguous labels consistently;
  • separate training, validation, and test examples; and
  • represent scenarios expected in production, rather than merely repeating a few phrases.

3. Annotation tools: Prodigy and BRAT

3.1 Why use a tool?

Hand-authoring JSON or span offsets is error-prone and impractical at scale. Annotation tools show text in an interface, allow spans and labels to be selected, record decisions, and export structured data.

3.2 Prodigy

Prodigy is a modern commercial annotation tool from the creators of spaCy. It is neither free nor open source, but it integrates tightly with the spaCy ecosystem and is intended for efficient, industrial annotation workflows. The lecture demonstrated its web demo to explain the general annotation process.

Typical workflow:

  1. One text sample appears in a clean web interface.
  2. Available entity types appear in the top bar (the example used PERSON and ORG).
  3. Choose an entity type.
  4. Select the corresponding text span with the cursor.
  5. Mark all required spans, such as a person’s name or US Navy as an organization.
  6. Decide whether to accept, reject, or ignore the sample.
  7. Save the session and export the annotations for training.

Decision meanings:

Decision Use
Accept text is relevant and the proposed/completed annotation is correct; add it to the dataset
Reject proposed analysis is wrong or the presented example should be explicitly rejected
Ignore example entered the pool but is irrelevant/uncertain and should not currently train the model

Benefits discussed:

  • tight spaCy integration;
  • reduced manual effort;
  • efficient annotation of large datasets;
  • structured export usable in the training workflow; and
  • an industry-oriented interface.

Limitations discussed:

  • paid commercial license;
  • not open source; and
  • licensing/seat requirements must be checked before organizational use.

3.3 BRAT

BRAT means Brat Rapid Annotation Tool. It is a free, open-source, web-based text annotation system and can also be installed locally.

Capabilities discussed:

  • named-entity/span annotation;
  • relation annotation between two or more entities;
  • demo datasets (the lecture referred to a CoNLL-style example);
  • browser-based annotation;
  • local installation, useful for private or restricted data; and
  • structured export that can be converted for spaCy training.

Basic workflow:

  1. Open the demo or install BRAT locally.
  2. Upload a small subset of the dataset.
  3. Select entity spans and labels.
  4. Optionally annotate relations.
  5. Export the results.
  6. Convert/validate them into the exact format expected by the spaCy training process.

3.4 Prodigy vs BRAT

Criterion Prodigy BRAT
Cost Commercial Free
Source Closed Open source
spaCy integration Very tight Compatible, often through conversion
Entity annotation Yes Yes
Relation annotation Supported by relevant recipes/workflows Yes; a notable core feature
Local/private use Available under its license Easily locally installed
Best fit production teams wanting an optimized spaCy workflow learning, research, budget-sensitive or privacy-controlled annotation

Practical selection rule: Choose a tool based on the target model’s input requirements, privacy constraints, scale, budget, collaboration needs, and export compatibility—not merely popularity.

3.5 File-format caveat

The lectures repeatedly describe spaCy training as consuming JSON. Conceptually, JSON is a convenient interchange/export format for annotations. In a current spaCy v3 project, training is commonly driven by a configuration file and serialized DocBin corpora (.spacy files), so exported JSON may require conversion. For exam answers tied to the lecture, state that annotation tools export structured labeled data/JSON for the spaCy training workflow; in implementation, verify the installed spaCy version’s expected format.

4. spaCy objects needed for training

4.1 Pipeline and components

A spaCy language pipeline (nlp) includes components such as:

  • tokenizer — segments text into tokens;
  • tagger — predicts POS/morphological information;
  • dependency parser — predicts syntactic relationships;
  • named entity recognizer (ner) — predicts labeled entity spans.

Some components are statistical/trainable. Updating one component can alter shared model behavior, so fine-tuning must be controlled.

4.2 Doc

Calling nlp(text) runs the pipeline and returns a Doc. For training examples, nlp.make_doc(text) is often preferable because it tokenizes without running all trained components.

4.3 Example

Raw (text, dictionary) pairs are not passed directly to nlp.update() in modern spaCy. They are converted to Example objects:

import spacy
from spacy.training import Example

nlp = spacy.load("en_core_web_md")
text = "I will visit you in Munich."
annotations = {"entities": [(20, 26, "GPE")]}

doc = nlp.make_doc(text)
example = Example.from_dict(doc, annotations)

Example.from_dict():

  • connects the text’s tokenization to the gold annotation;
  • creates aligned predicted/reference representations;
  • translates character-offset supervision into a form used by the training machinery; and
  • enables the model’s output to be compared with the correct answer to compute loss.

Exam distinction: A Doc contains tokenized/processed text. An Example pairs the model-side document with reference (gold) annotations for training/evaluation.

5. How statistical training works

5.1 Epochs

An epoch is one complete pass through the training dataset. The lecture examples used 20 epochs for navigation fine-tuning and 25 for the small medical model. These are demonstrations, not universal optimum values.

5.2 Shuffling

At every epoch, shuffle the examples:

random.shuffle(TRAIN_DATA)

Shuffling prevents a fixed ordering from systematically biasing the updates and helps stochastic optimization train more thoroughly. random.shuffle() changes the sequence in place. Python’s random module supplies pseudo-random methods for distributions including uniform, gamma, and beta; this example specifically needs shuffle.

5.3 Loss

The loss function measures disagreement between the gold annotation and the model’s current output. Training seeks parameters that minimize this loss.

Conceptually:

prediction + gold label → loss → optimizer → adjusted weights

nlp.update() returns/updates loss information each time it trains on examples. Exact loss values may differ between runs because of random initialization and shuffle order.

5.4 Optimizer and stochastic gradient descent

An optimizer updates neural-network weights with respect to the loss. The lecture explains this through stochastic gradient descent (SGD): start at a point on the loss surface and take steps down the slope toward a lower value.

Simplified rule:

\[ \theta_{t+1}=\theta_t-\eta\nabla_{\theta}L(\theta_t) \]

where:

  • \(\theta\) = parameters/weights;
  • \(L\) = loss;
  • \(\nabla L\) = direction of steepest increase;
  • \(\eta\) = learning rate/step size.

Because subtraction moves against the gradient, the update aims to reduce loss.

5.5 Avoiding catastrophic forgetting

When fine-tuning a pretrained NER model on a narrow domain, it may forget previously learned entity behavior. Risk-reduction measures include:

  • disable unrelated components;
  • continue from the existing optimizer/weights rather than reinitializing;
  • include representative old/general examples where retaining prior capabilities matters;
  • use diverse, balanced data; and
  • evaluate both new-domain and original-domain behavior.

6. Updating an existing NER pipeline: navigation domain

6.1 Goal

The first training exercise updates the NER component of pretrained en_core_web_md so it performs better on navigation-specific locations such as home, office, streets, and districts.

The three stated steps were:

  1. disable all other statistical components, such as tagger and parser;
  2. train NER with domain examples; and
  3. evaluate the updated NER.

The updated model is then saved to disk and loaded when needed.

6.2 Why disable other components?

Only NER has gold supervision in this exercise. Leaving other statistical pipes active would:

  • waste computation;
  • expose components to updates without their own correct targets;
  • risk degrading already useful POS/parser behavior; and
  • make it harder to isolate the intended change.

The tokenizer is not a regular statistical pipe to disable in this manner; it is required to create the Doc.

6.3 Representative training data

TRAIN_SET = [
    ("Navigate home", {"entities": [(9, 13, "GPE")]}),
    ("Navigate to office", {"entities": [(12, 18, "GPE")]}),
    ("Navigate", {"entities": []}),
    ("Navigate to Oxford Street", {"entities": [(12, 25, "GPE")]}),
]

These examples illustrate destination entities and one negative command. In a real system, a more semantically precise custom label such as DESTINATION may be preferable to overloading GPE, because home and office are not geopolitical entities.

6.4 Complete fine-tuning pattern

import random
import spacy
from spacy.training import Example

nlp = spacy.load("en_core_web_md")
epochs = 20

other_pipes = [pipe for pipe in nlp.pipe_names if pipe != "ner"]

with nlp.disable_pipes(*other_pipes):
    optimizer = nlp.create_optimizer()

    for epoch in range(epochs):
        random.shuffle(TRAIN_SET)
        losses = {}
        examples = []

        for text, annotations in TRAIN_SET:
            doc = nlp.make_doc(text)
            examples.append(Example.from_dict(doc, annotations))

        nlp.update(examples, sgd=optimizer, losses=losses)
        print(epoch, losses)

Important mechanics:

  • nlp.pipe_names lists active pipeline components.
  • The list comprehension retains every name other than ner.
  • with nlp.disable_pipes(*other_pipes): temporarily disables them as a context manager; the pipes are restored after the block.
  • *other_pipes unpacks the list into separate arguments.
  • nlp.create_optimizer() continues training an existing initialized pipeline.
  • Each raw pair becomes an Example.
  • nlp.update(...) calculates loss, backpropagates, and lets the optimizer update weights.

6.5 Save and reload

Save the complete pipeline, not merely a visualization:

output_dir = "navigation_ner"
nlp.to_disk(output_dir)

reloaded_nlp = spacy.load(output_dir)

displaCy only renders analysis; it does not save model parameters.

6.6 Evaluation

Test on unseen variations:

for text in [
    "Take me home",
    "Navigate to Oxford Street",
    "Please start navigation",       # expected negative
    "Meet me in London",             # checks retained general knowledge
]:
    doc = nlp(text)
    print(text, [(ent.text, ent.label_) for ent in doc.ents])

For a proper evaluation, calculate precision, recall, and F1 on a held-out test set rather than treating falling training loss as proof of generalization.

7. Training a blank medical NER model from scratch

7.1 Why start from scratch?

The lecture’s medical example assumes the general spaCy NER does not adequately recognize the required medical categories. Instead of adapting general labels, it creates a blank English pipeline and trains NER only for:

  • DRUG — drug names;
  • DIS — diseases.

This is different from fine-tuning:

Fine-tuning existing model Training blank model
begins with pretrained pipeline/NER weights begins with blank language pipeline/component
tries to preserve prior knowledge deliberately learns only the supplied schema
uses create_optimizer() in the lecture initializes training with initialize()/historically begin_training()
less data may be needed for modest adaptation requires enough labeled data to learn everything desired

7.2 Demonstration dataset

The spoken transcript’s drug names and offsets are noisy, but its intended structure is:

TRAIN_DATA = [
    ("Methylphenidate is used in treating children with epilepsy.",
     {"entities": [
         (0, 15, "DRUG"),
         (51, 59, "DIS")
     ]}),
    ("Patients were followed up for six months.",
     {"entities": []}),
    ("An antibiotic may be useful for coronary artery disease.",
     {"entities": [
         (3, 13, "DRUG"),
         (32, 55, "DIS")
     ]}),
]

Always recompute and validate actual offsets from the final exact strings. The learning points are the two-label schema and inclusion of an empty example.

7.3 Blank pipeline and labels

import random
import spacy
from spacy.training import Example

nlp = spacy.blank("en")
ner = nlp.add_pipe("ner")

for label in ["DRUG", "DIS"]:
    ner.add_label(label)
  • spacy.blank("en") creates an English language object without pretrained statistical components.
  • nlp.add_pipe("ner") adds a new blank entity recognizer.
  • ner.add_label(label) declares every class it must predict.

7.4 Initialization and training

The lecture used the older nlp.begin_training() wording and explained that the blank model’s weights are initialized so it learns from scratch. In current spaCy, the explicit initialization pattern is:

def get_examples():
    for text, annotations in TRAIN_DATA:
        yield Example.from_dict(nlp.make_doc(text), annotations)

optimizer = nlp.initialize(get_examples=get_examples)

for epoch in range(25):
    random.shuffle(TRAIN_DATA)
    losses = {}

    examples = [
        Example.from_dict(nlp.make_doc(text), annotations)
        for text, annotations in TRAIN_DATA
    ]
    nlp.update(examples, sgd=optimizer, losses=losses)
    print(epoch, losses)

If other components exist, disable all except ner in the same context-manager pattern used above.

7.5 Positive and negative testing

Positive medical test:

doc = nlp("I had coronary artery disease.")
print([(ent.text, ent.label_) for ent in doc.ents])

The lecture also checks the first entity’s label through doc.ents[0].label_.

Negative/general-domain tests:

print(nlp("I met you at Trump Tower.").ents)
print(nlp("I will meet you in San Francisco.").ents)

The expected result for this deliberately narrow blank model is no entity, because it learned only DRUG and DIS, not general ORG, FAC, or GPE knowledge.

This demonstrates both the benefit and cost of training from scratch: the schema is controlled, but general pretrained capabilities are absent unless explicitly taught.

7.6 Visualize with displaCy

from spacy import displacy

doc = nlp("I had coronary artery disease.")
displacy.serve(doc, style="ent")

Use style="ent" for entity visualization. displacy.render(..., jupyter=True) is more convenient inside a notebook; serve starts a local visualization server.

7.7 Real-production caveat

Three examples are enough to demonstrate code, not to create a dependable medical system. A production model needs:

  • substantially more expert-labeled data;
  • clear clinical annotation guidelines;
  • patient/privacy safeguards;
  • held-out evaluation and error analysis;
  • coverage of abbreviations, misspellings, multiword terms, negation contexts, and ambiguous names; and
  • domain-expert validation before any clinical use.

8. Case study: named entities in airline reviews

8.1 Business task

The case study processes an airline-review CSV to:

  1. inspect entities in the first 20 reviews;
  2. visualize them;
  3. process up to 5,000 reviews;
  4. find the 10 most frequent entity strings; and
  5. decide which extracted entities are actually relevant to travel/marketing analysis.

This case distinguishes three layers:

spaCy NER = linguistic extraction
Counter    = frequency aggregation
analyst    = relevance validation and business interpretation

8.2 Imports and model loading

import pandas as pd
import spacy
from spacy import displacy

nlp = spacy.load("en_core_web_md")
df = pd.read_csv("AirlineReview.csv")

The lecture also showed importing en_core_web_md as a Python package and calling its load() method. spacy.load("en_core_web_md") is the usual compact equivalent.

Inspect column names and missing values before assuming the review column is called review:

print(df.columns)
reviews = df["review"].dropna().astype(str)

8.3 Inspect the first 20 reviews

for i, review in enumerate(reviews.iloc[:20], start=1):
    doc = nlp(review)
    print(f"Review #{i}: {review}")
    for ent in doc.ents:
        print(f"  Entity: {ent.text} — Label: {ent.label_}")
    print()

Key objects:

  • nlp(review) runs the full spaCy pipeline.
  • The result is a Doc containing tokens, linguistic annotations, and entities.
  • doc.ents is the sequence of recognized entity spans.
  • ent.text gives the surface text.
  • ent.label_ gives the readable category string.

8.4 Visualization

for review in reviews.iloc[:20]:
    doc = nlp(review)
    displacy.render(doc, style="ent", jupyter=True)

displaCy provides qualitative validation: it shows entity boundaries and types in context, making false positives, missing spans, and questionable labels easier to notice.

It does not:

  • perform NER itself;
  • change model predictions;
  • count frequencies; or
  • save/retrain the model.

8.5 Count entities over 5,000 reviews

from collections import Counter

entity_counter = Counter()

for review in reviews.iloc[:5000]:
    doc = nlp(review)
    for ent in doc.ents:
        entity_counter[ent.text] += 1

for entity, frequency in entity_counter.most_common(10):
    print(f"Entity: {entity}; Frequency: {frequency}")

Counter is a dictionary-like frequency accumulator. It does no linguistic analysis; it counts what spaCy has already extracted. most_common(10) sorts and returns the ten largest counts.

The classroom run reported a very frequent first (about 756 occurrences, labeled ORDINAL) and Toronto (about 200, a GPE). Exact results depend on the dataset slice, preprocessing, and model version.

8.6 Efficient batch processing

For larger data, use nlp.pipe() rather than repeatedly calling nlp() in Python:

entity_counter = Counter()

for doc in nlp.pipe(reviews.iloc[:5000], batch_size=64):
    for ent in doc.ents:
        entity_counter[(ent.text, ent.label_)] += 1

Counting (text, label) rather than text alone prevents two meanings/categories with the same surface form from being silently combined.

Normalization can also improve aggregation:

key = (ent.text.strip().casefold(), ent.label_)

But normalization must be chosen carefully; collapsing capitalization or aliases can sometimes merge distinct entities. For destination analysis, a curated alias map might combine NYC, New York, and New York City.

9. From raw entity counts to useful business insight

9.1 Frequency is not importance

The most frequent extracted string is not automatically the most useful. first may be linguistically correct as ORDINAL, yet irrelevant to a campaign studying destinations. Toronto may occur less frequently but be far more actionable.

Therefore:

high frequency ≠ high business value
correct linguistic label ≠ relevance to the project

9.2 Signal and noise

  • Signal: entities aligned with the objective, e.g. GPE, LOC, or possibly FAC for destination/airport analysis.
  • Noise: correct or incorrect extractions that do not answer the business question, e.g. ORDINAL values in a location campaign.

Poorly filtered output can produce poor marketing decisions even when the model itself is behaving as designed.

9.3 Immediate solution: filter by label

If the pretrained model recognizes locations adequately, filter before counting:

LOCATION_LABELS = {"GPE", "LOC", "FAC"}
location_counter = Counter()

for doc in nlp.pipe(reviews.iloc[:5000], batch_size=64):
    for ent in doc.ents:
        if ent.label_ in LOCATION_LABELS:
            location_counter[ent.text] += 1

print(location_counter.most_common(10))

Advantages:

  • fast;
  • cheap;
  • easy to explain;
  • immediately aligned with the business objective; and
  • does not require retraining.

Limitation: post-processing changes the analysis output, not the model. Any missed or wrongly labeled location remains wrong.

9.4 GPU acceleration

A GPU/TPU may reduce processing time for large corpora and prevent impractically slow inference. It is relevant when throughput is the bottleneck.

However:

  • it does not decide which labels matter;
  • it does not remove noisy entity categories;
  • it does not improve the learned accuracy merely by running on a GPU; and
  • hardware cost/availability can rise.

Exam distinction: GPU addresses speed and scale, not semantic relevance or model quality.

9.5 Custom NER training

Custom training is appropriate when the general model systematically fails to recognize domain entities, boundaries, aliases, airport codes, route names, product names, or organization-specific concepts.

Benefits:

  • domain-specific label schema;
  • better long-term alignment;
  • potential reduction in systematic false positives/negatives; and
  • recognition of entities absent from generic models.

Costs:

  • annotation time and expert effort;
  • compute and experimentation;
  • validation and maintenance;
  • model/version management; and
  • risk of catastrophic forgetting during fine-tuning.

For the immediate airline question, if GPE extraction is already usable and the main problem is that ORDINAL results pollute the top-ten list, filtering is preferable to retraining. Retraining becomes justified when filtering cannot recover missing or misclassified domain entities.

9.6 Recommended business-intelligence pipeline

Customer reviews
      ↓
NER inference
      ↓
qualitative validation with contextual samples/displaCy
      ↓
entity-type filtering and text normalization
      ↓
frequency aggregation
      ↓
human/business validation
      ↓
marketing insight and decision

The lecturer’s broader data-science message is to validate before interpreting. Ask:

  • Is the extraction correct?
  • Is it relevant?
  • Is it aligned with the project goal?
  • Is the frequency driven by duplicates, boilerplate, or spelling variants?
  • Does sentiment/context change the interpretation? A frequently named destination may be frequently criticized rather than preferred.

Practical extension: join location entities with review sentiment and airline/route metadata to distinguish popular and praised, popular and criticized, and merely mentioned destinations.

10. Choosing among filtering, hardware, and custom training

Option Problem solved Advantages Limitations Choose when
Filter labels irrelevant entity categories in output immediate, simple, cheap does not change predictions model is mostly correct; only analysis scope is narrower
GPU acceleration slow inference/large volume greater throughput no inherent accuracy/relevance gain speed is the actual bottleneck
Fine-tune/custom NER domain mismatch improves domain recognition annotation, evaluation, compute, maintenance generic model repeatedly misses/mislabels important domain concepts

Short-term recommendation for the case study: filter to relevant location labels and validate. Long-term recommendation: collect corrected examples and train a domain model only if recurring model errors justify the investment.

11. Common errors and misconceptions

  1. “Raw text alone can train supervised NER.” False. NER requires gold spans/labels (or another explicit supervision strategy).
  2. “Offsets are word indices.” False. They are zero-based character boundaries.
  3. “The end offset is inclusive.” False. It is exclusive.
  4. “Negative sentences should be deleted.” False. Correct empty examples teach the model not to hallucinate entities.
  5. “A raw annotation dictionary can always be sent directly to nlp.update().” In modern spaCy, create Example objects.
  6. “Train every pipeline component at once.” Not when only NER is supervised; disable unrelated statistical components.
  7. “create_optimizer() and initialization mean the same thing.” No. Continuing a pretrained model aims to preserve learned weights; initializing a blank model establishes new weights for learning from scratch.
  8. “Training loss proves quality.” No. Evaluate on held-out unseen examples.
  9. “displaCy performs NER.” No. The pipeline predicts; displaCy visualizes.
  10. “Counter performs NLP.” No. It aggregates already extracted strings.
  11. “The most common entity is the most important.” Not necessarily; relevance depends on the business objective.
  12. “A GPU improves prediction accuracy.” It generally improves speed/throughput, not learned quality.
  13. “Filtering retrains the model.” It only changes downstream output.
  14. “Custom training is always best.” It is expensive and unnecessary if a simple filter solves the requirement.
  15. “A three-sentence medical model is production-ready.” It is only a teaching demonstration.
  16. “Saving a visualization saves the model.” Use nlp.to_disk() and reload with spacy.load().

12. High-yield comparisons for the exam

12.1 nlp(text) vs nlp.make_doc(text)

nlp(text) nlp.make_doc(text)
tokenizes and runs active pipeline components tokenizes only
used for inference useful when constructing training examples
produces predictions including doc.ents avoids unnecessary/current predictions during example creation

12.2 Updating vs training from scratch

  • Update/fine-tune: load en_core_web_md, isolate NER, continue optimizing with domain examples, test retention.
  • Scratch: spacy.blank("en"), add ner, add labels, initialize, train entirely from annotated examples, expect no general NER knowledge.

12.3 Annotation vs inference vs analysis

  • Annotation: humans/tools provide correct labels for learning.
  • Training: optimizer adjusts weights to reduce loss on examples.
  • Inference: nlp(text) predicts entities in unseen text.
  • Visualization: displaCy displays predictions.
  • Aggregation: Counter calculates frequencies.
  • Business analysis: filters, validates, contextualizes, and interprets results.

13. Likely exam questions and model-answer points

Q1. Explain the NER training-data structure in spaCy.

State that each example pairs a sentence with an annotation dictionary. Each entity is (start, end, label), using zero-based, end-exclusive character offsets. Empty-entity sentences use {"entities": []} and are valuable negative examples. Convert the data to Example objects before updating the model.

Q2. Why are other spaCy pipes disabled while training NER?

Only NER receives correct supervision. Disabling tagger/parser reduces computation and protects unrelated learned parameters. disable_pipes is used as a context manager, and the other pipes return afterward.

Q3. Differentiate create_optimizer() and training initialization.

create_optimizer() in the lecture continues from an existing pretrained pipeline to reduce forgetting. begin_training() was used for a blank model; current spaCy typically uses nlp.initialize(). Initialization prepares the blank model/optimizer using the supplied examples.

Q4. Why include an example with no entities?

It is negative supervision. It teaches the decision boundary and reduces the tendency to force an entity prediction into every sentence, improving precision and real-world generalization.

Q5. Compare Prodigy and BRAT.

Prodigy is commercial, from spaCy’s creators, efficient, and tightly integrated. BRAT is free/open source, web-based/local, and supports entity and relation annotation. Both structure labels for a training workflow, but conversion/compatibility requirements must be verified.

Q6. Explain the airline-review entity-frequency pipeline.

Load CSV with pandas; load the spaCy model; process sample reviews; inspect doc.ents, ent.text, and ent.label_; visualize with displaCy; process the larger corpus; count with Counter; obtain most_common(10); validate and filter labels before interpreting the result.

Q7. Why is first being the most frequent entity not necessarily useful?

It may be a correct ORDINAL, but a destination campaign needs location entities. Frequency measures occurrence, not relevance. Filter to GPE/LOC/appropriate labels and validate context.

Q8. When should filtering, a GPU, or custom training be chosen?

  • Filter when predictions are broadly correct but irrelevant categories appear.
  • Use a GPU when processing speed/volume is the bottleneck.
  • Train custom NER when the generic model systematically fails on domain entities and the expected long-term value exceeds annotation and maintenance cost.

Q9. How is a trained model saved and used later?

Call nlp.to_disk(path) to serialize the pipeline and spacy.load(path) to reload it. Test the reloaded model on held-out examples.

Review-Week Augmentation

The review links annotation quality to continuous production learning. Customer language changes with products, services, abbreviations, policies, and failure modes, so the lifecycle should be:

\[ \text{logs} \rightarrow \text{unknown/error analysis} \rightarrow \text{human-validated labels} \rightarrow \text{updated data} \rightarrow \text{retrain} \rightarrow \text{evaluate} \rightarrow \text{deploy}. \]

Do not automatically treat model predictions as ground truth: an error can become a training label and be reinforced. Apply confidence filtering, human review where needed, duplicate detection, privacy controls, representative sampling, and annotation-quality checks. Unknown intents are valuable candidates for analysis and future annotation, but only after validation.
