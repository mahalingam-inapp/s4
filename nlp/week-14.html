Learning map

Week 14 connects the complete applied NLP workflow:

  1. choose a pretrained checkpoint appropriate to a task;
  2. prepare and tokenize task-specific data;
  3. use a high-level pipeline for quick inference or a model/tokenizer pair for control;
  4. fine-tune efficiently rather than train a large model from scratch;
  5. evaluate with overall and class-wise metrics;
  6. diagnose errors before spending more compute;
  7. deploy an interactive demonstration through Hugging Face Spaces.

The examples cover Yelp review classification, financial-news sentiment with Llama 2, abstractive summarization with T5, and deployment through Spaces.

1. Hugging Face Spaces

Definition and purpose

A Hugging Face Space hosts an ML demonstration application directly on a personal or organization profile. It is useful for:

  • building an ML portfolio;
  • demonstrating work at conferences;
  • presenting models to business stakeholders;
  • sharing reproducible applications rather than only source code;
  • collaborating with the wider ML community.

Users visit a browser-based application; they ordinarily do not need to clone the repository, install packages, or run the model locally. A normal repository mainly exposes files, whereas a Space builds and runs an application from the repository.

Supported application types

  • Gradio: rapid Python interfaces for model inputs and outputs.
  • Streamlit: interactive Python data/ML applications.
  • Docker: arbitrary applications and custom system environments through a Dockerfile.
  • Static: HTML and JavaScript applications.

Spaces can be forked. A fork creates a separate copy that can be modified without altering the original, which is valuable for experimentation and collaboration.

Default environment and dependencies

The Space environment includes several useful components:

  • huggingface_hub: manage Hub repositories/files and programmatically access inference APIs;
  • requests: call third-party APIs;
  • datasets: fetch and display Hub datasets;
  • the chosen SDK, such as Gradio or Streamlit;
  • common Debian packages such as FFmpeg, CMake, and libsm6.

Using the hosted inference API can exploit built-in acceleration, avoid instantiating a large model inside the app, and reduce local compute/resource consumption.

Dependency files have distinct roles:

File Purpose Installation mechanism
pre-requirements.txt Dependencies needed before the main environment; e.g., upgrade pip Python package installation first
requirements.txt Python libraries needed by the application pip
packages.txt Debian/system packages, one package per line apt-get install

These files must be at the repository root. requirements.txt and packages.txt are not interchangeable.

Space configuration

Appearance and runtime settings are placed in a YAML front-matter block at the top of the root README.md. A typical Gradio Space may specify:

---
title: Demo Space
emoji: 🤗
colorFrom: yellow
colorTo: orange
sdk: gradio
app_file: app.py
pinned: false
---

The runtime reads this metadata to determine the SDK and application entry point.

Practical use case

A bank’s NLP team can publish a financial-news sentiment demo. An analyst pastes a headline, the hosted app runs the classifier, and the browser displays positive/neutral/negative sentiment. A Space makes the artifact immediately demonstrable to stakeholders while preserving the model and app code in a versioned repository.

2. Checkpoints, Auto classes, and task suitability

Hugging Face Transformers exposes thousands of pretrained models for tasks such as:

  • sequence classification and sentiment analysis;
  • question answering;
  • named-entity recognition/token classification;
  • summarization;
  • translation and other sequence-to-sequence tasks;
  • zero-shot classification.

Auto classes select the correct architecture from a checkpoint, e.g. AutoTokenizer, AutoModelForSequenceClassification, and AutoModelForSeq2SeqLM.

Critical checkpoint rule

A model performs well only when the checkpoint is appropriate for the task. Most checkpoints are:

  1. pretrained on a large corpus to learn general language patterns; and then
  2. fine-tuned on a specific task and dataset.

Therefore:

  • not every model has been fine-tuned for every task;
  • a task-fine-tuned checkpoint may still mismatch the user’s domain;
  • the checkpoint’s original dataset may or may not overlap with the deployment use case;
  • use the task example scripts (often run_$TASK.py) or a custom training script when adaptation is required.

Example: a general sentiment model trained on product reviews may misunderstand “liability increased” or “guidance was cut” in financial news. Domain-specific fine-tuning is justified even though both problems are called sentiment analysis.

3. Inference choices: pipeline() versus direct model use

pipeline()

pipeline() is a high-level inference abstraction. It combines preprocessing, model execution, and output postprocessing, often in about two lines:

from transformers import pipeline

classifier = pipeline("sentiment-analysis")
classifier("The company raised its earnings forecast.")

Best for quick prototypes, standard tasks, demonstrations, and applications where default tokenization/output behavior is adequate.

Model plus tokenizer

Direct usage provides access to token IDs, attention masks, padding/truncation, devices, logits, hidden states, batching, PyTorch/TensorFlow tensors, and custom postprocessing:

from transformers import AutoTokenizer, AutoModelForSequenceClassification

checkpoint = "google-bert/bert-base-cased"
tokenizer = AutoTokenizer.from_pretrained(checkpoint)
model = AutoModelForSequenceClassification.from_pretrained(checkpoint, num_labels=5)

batch = tokenizer(texts, padding=True, truncation=True, return_tensors="pt")
outputs = model(**batch)
logits = outputs.logits

Exam comparison

Requirement Prefer
Fast standard inference pipeline()
Minimum code pipeline()
Raw logits/hidden states model + tokenizer
Custom tokenization/batching model + tokenizer
Fine-tuning Trainer/custom loop, not pipeline()
Detailed model control model + tokenizer

pipeline() performs inference; it does not itself fine-tune a model.

4. Zero-shot, one-shot, and few-shot learning

Supervised learning

In standard supervised classification/regression, labels define both the possible outputs and the ground truth for each training instance. Learning adjusts weights to minimize prediction error relative to ground truth. It commonly requires many labeled examples and repeated updates.

Large-scale annotation is expensive and slow. Some classes—rare diseases, newly discovered species, rare financial events—may have few or no examples. Humans can distinguish roughly 30,000 object categories, making explicit labeled training for every possible class impractical in time, cost, and compute.

N-shot spectrum

  • Zero-shot learning (ZSL): predict an unseen class without any labeled training example for that class.
  • One-shot learning: use one labeled example.
  • Few-shot learning (FSL): use a small number of labeled examples, often through transfer learning or meta-learning.

“Zero-shot” describes the learning problem, not one particular algorithm or architecture. It does not necessarily mean that the concept never appeared in pretraining; it means the model received no labeled examples for that unseen class in task training. Large language models are suited to ZSL because self-supervised pretraining over massive corpora may provide incidental knowledge of the concepts.

Without task labels, ZSL relies on auxiliary semantic knowledge, such as natural-language class descriptions or relationships between seen and unseen classes. It is important in computer vision and NLP.

Fluent zero-shot output is not proof of benchmark alignment. Evaluate against labeled data before trusting it in a domain-sensitive application.

5. Fine-tuning pretrained transformers

Definition and benefits

Fine-tuning continues training a pretrained model on a dataset specific to the target task. It reduces computation cost, carbon footprint, time, and data needs, while providing access to state-of-the-art representations. It is different from:

  • training from scratch, which initializes all model weights without pretrained knowledge;
  • prompting, which changes the input but does not update weights;
  • frozen feature extraction, where pretrained weights remain fixed and only a new head or downstream model is learned.

Fine-tuning is appropriate when prompting or a generic checkpoint does not reliably align outputs with the task, label definitions, or domain language.

Yelp review sequence-classification workflow

The transcript demonstrates five-class Yelp review classification.

1. Load and inspect data

from datasets import load_dataset

dataset = load_dataset("yelp_review_full")
dataset["train"][0]

The dataset contains review text and a label. The lecturer first examines a small portion and later creates compact train/evaluation subsets to shorten training time.

2. Load tokenizer and preprocess

from transformers import AutoTokenizer

checkpoint = "google-bert/bert-base-cased"
tokenizer = AutoTokenizer.from_pretrained(checkpoint)

def tokenize_function(examples):
    return tokenizer(
        examples["text"],
        padding="max_length",
        truncation=True,
    )

tokenized_datasets = dataset.map(tokenize_function, batched=True)
  • Padding makes variable-length examples compatible within a batch.
  • Truncation prevents examples from exceeding the model’s supported/selected maximum length.
  • map() applies the same transformation over the dataset.
  • batched=True processes multiple records at once and improves preprocessing throughput.

3. Make reproducible small subsets

small_train_dataset = (
    tokenized_datasets["train"].shuffle(seed=42).select(range(1000))
)
small_eval_dataset = (
    tokenized_datasets["test"].shuffle(seed=42).select(range(1000))
)

The same fixed seed gives reproducible sampling. A smaller subset speeds demonstration but may reduce representativeness and should not be confused with a production-quality experiment.

4. Load a task head

from transformers import AutoModelForSequenceClassification

model = AutoModelForSequenceClassification.from_pretrained(
    checkpoint,
    num_labels=5,
)

The Yelp dataset has five labels. When loading base BERT into a sequence classifier, warnings that some pretrained weights are unused and classification-head weights are newly/randomly initialized are normal: the pretraining head is discarded and a task-specific classification head is attached. That new head must be trained.

Use exact API spelling: from_pretrained, not from_pre_trained, from_pretrainer, or similar transcript typos.

5. Train with the PyTorch Trainer

Trainer avoids manually writing the complete training loop. Its API supports logging, gradient accumulation, mixed precision, evaluation, checkpointing, and other training options. Conceptually:

from transformers import TrainingArguments, Trainer

args = TrainingArguments(
    output_dir="yelp_model",
    evaluation_strategy="epoch",
    num_train_epochs=3,
)

trainer = Trainer(
    model=model,
    args=args,
    train_dataset=small_train_dataset,
    eval_dataset=small_eval_dataset,
    tokenizer=tokenizer,
)
trainer.train()

Exact keyword names can vary by installed Transformers version; the underlying concepts are model, training arguments, train data, evaluation data, tokenizer/data collator, and metrics.

6. Financial-news sentiment with Llama 2

Business problem

Classify a financial sentence as positive, neutral, or negative from an investor’s perspective, i.e. by its likely impact on stock price. Applications include:

  • market monitoring;
  • investment decisions;
  • risk management;
  • alert prioritization;
  • portfolio/news dashboards.

The example uses the Financial PhraseBank, introduced by Aalto University School of Business researchers in 2014. It contains about 5,000 human-annotated financial sentences. Annotators judge likely positive, neutral, or negative stock-price impact from an investor viewpoint. Such domain-annotated data is scarce because much financial data is proprietary.

Hardware and model constraints

In Colab, select Runtime -> Change runtime type -> T4 GPU when available. A 7B-parameter model is costly to hold and train at full precision. Resource-aware options include:

  • quantization to reduce weight memory;
  • parameter-efficient fine-tuning (PEFT);
  • LoRA adapters;
  • small controlled subsets/runs;
  • gradient accumulation or mixed precision;
  • targeted rather than exhaustive hyperparameter search.

Quantization versus LoRA

Quantization stores/computes weights at reduced precision, commonly through bitsandbytes, primarily reducing memory and sometimes improving feasible throughput. It does not by itself perform task adaptation.

LoRA (Low-Rank Adaptation) freezes the base weight matrix and learns low-rank updates:

\[ W' = W + BA \]

where the rank \(r\) controls adapter capacity. Higher rank can model more complex task-specific changes but increases trainable parameters, memory, and computation. Quantization and LoRA solve different problems and can be combined (often called QLoRA).

Data preparation and schema discipline

An end-to-end preparation workflow should:

  1. load data into Pandas;
  2. inspect columns, types, missing values, and label values;
  3. clean/rename columns deliberately;
  4. map labels into the required representation;
  5. split train/test before any leakage-prone resampling;
  6. create instruction-style prompts;
  7. convert the validated DataFrame to a Hugging Face Dataset.

A Pandas KeyError: 'sentiment' means that the referenced column is absent at that point—perhaps it was named differently, renamed, dropped, misspelled, or whitespace/case differs. Diagnose with:

print(df.columns.tolist())
print(df.head())
print(df.dtypes)

Then use the actual column name or rename it once. Quantization, model loading, and Dataset.from_pandas() cannot repair an invalid DataFrame schema. Treat column names as a schema contract across preprocessing, prompt creation, training, and evaluation.

Balanced sampling and replacement

If each sentiment is sampled to create a balanced set, distinguish:

  • replace=False: an original row can be selected at most once; impossible to request more rows than a class contains.
  • replace=True: the same row may be selected multiple times; permits oversampling but creates duplicates, not new information.

Balancing makes each class contribute similarly to training/evaluation, but it does not ensure qualitative diversity or match real deployment prevalence. Duplicate evaluation records can narrow confidence and distort an estimate. Most importantly, replacement does not prevent data leakage.

Leakage occurs when identical/near-identical examples or information derived from the test set enters training. Split original unique records first, then oversample only the training partition. Keep test records untouched and check overlap using stable row IDs or normalized text hashes.

Prompt construction

Instruction prompts should define:

  • the role/task: classify financial sentiment;
  • allowed labels: positive, neutral, negative;
  • the investor/stock-price perspective;
  • strict desired output format;
  • the input sentence;
  • optionally representative demonstrations.

Training and inference formatting should remain consistent. Prompting changes context only; supervised fine-tuning updates weights. Begin with a zero/few-shot baseline and fine-tune when measured errors show inadequate alignment.

Evaluation function

The transcript proposes mapping labels to numeric values (positive 2, neutral 1, negative 0), then computing accuracy, a per-class classification report, and a confusion matrix.

\[ \text{Accuracy}=\frac{\text{correct predictions}}{\text{all predictions}} \]

\[ \text{Precision}=\frac{TP}{TP+FP},\qquad \text{Recall}=\frac{TP}{TP+FN} \]

\[ F_1=2\frac{\text{Precision}\times\text{Recall}} {\text{Precision}+\text{Recall}} \]

  • Precision: when the model predicts a class, how often is it correct?
  • Recall: of all true members of a class, how many were found?
  • F1: harmonic balance between precision and recall.
  • Confusion matrix: shows which true classes are being confused with which predicted classes.

For risk-sensitive financial sentiment, low negative recall is especially serious because truly negative news is missed (false negatives). Accuracy can hide this failure, particularly under imbalance.

Review/live-session case: Capital Insights Ltd.

The review case describes a team adapting a quantized 7B Llama 2 model with supervised fine-tuning, PEFT, and LoRA. The dataset is numerically balanced among positive, neutral, and negative labels, and instruction prompts define task/output structure.

A baseline reveals weak negative-class recall. After five epochs:

  • overall accuracy improves by eight percentage points;
  • positive and neutral F1 scores improve;
  • false positives decrease;
  • negative sentiment remains the weakest class.

This proves that balanced class counts do not guarantee balanced class-wise performance. Negative examples may lack qualitative diversity or may contain subtler linguistic patterns.

Two proposed changes are examined:

  • Increase LoRA rank: raises adaptation capacity, but also parameter count/memory/compute; useful only if adapter capacity is the bottleneck.
  • Increase batch size: may improve hardware utilization/training throughput and help meet a deadline, but needs more memory and does not directly solve poor negative recall.

Neither should be accepted automatically. The preferred method is:

\[ \text{Evaluate} \rightarrow \text{find false negatives} \rightarrow \text{qualitative error analysis} \rightarrow \text{targeted data/prompt improvement} \rightarrow \text{controlled experiment} \rightarrow \text{reevaluate} \]

A resource-efficient intervention is to inspect missed negative examples, identify recurring patterns (negation, guidance cuts, weak outlook, litigation, indirect loss language), add representative examples or clearer prompt guidance, keep LoRA rank and batch size fixed, run a short controlled experiment, and measure negative recall/F1. Escalate to broader rank/hyperparameter experiments only if the targeted intervention fails.

Lecturer/review emphasis: do not spend more compute until the error is understood. Choose the smallest measurable intervention that addresses the actual bottleneck under accuracy, memory, cost, and deadline constraints.

7. Case study: complete financial-sentiment system design

Data and preprocessing

  1. Acquire a large dataset from reliable sources such as Reuters, Bloomberg, and the Financial Times.
  2. Remove relevant noise such as HTML markup; consider punctuation and stop-word handling only when compatible with the model and task. Transformer tokenizers often preserve useful punctuation/negation, so do not clean blindly.
  3. Tokenize text.
  4. Normalize when appropriate through stemming or lemmatization; again, aggressive normalization may be unnecessary for pretrained transformers.
  5. audit data quality, bias, duplicates, missing values, label consistency, and class imbalance.

Modeling

  • Choose BERT, RoBERTa, ALBERT, or another architecture based on data size, latency, and compute.
  • Start from large-scale language-model pretraining to capture general linguistic patterns.
  • Fine-tune on financial news for task/domain adaptation.
  • Tune learning rate, batch size, and epochs through controlled experiments.
  • If imbalance is present, consider over/undersampling or class-aware loss, while preserving a realistic untouched test set.
  • Add domain-specific signals such as financial indicators or market sentiment where justified.
  • Ensembles using voting or stacking may improve accuracy/robustness, at additional complexity and latency.

Evaluation and explainability

  • Report accuracy, precision, recall, F1, and confusion matrix.
  • Use cross-validation where feasible to estimate generalization rather than relying on one favorable split.
  • Inspect attention or other explanation/error-analysis tools cautiously to understand influential features; attention is not automatically a complete causal explanation.

8. Case study: abstractive summarization with T5

Summarization types

  • Extractive summarization: selects the most relevant existing passages/sentences.
  • Abstractive summarization: generates new text that expresses the important information.

Summarization and translation can be formulated as sequence-to-sequence tasks. The demonstration fine-tunes T5-small for abstractive summarization on the California (ca_test) subset of BillSum, a legislative-bill summarization dataset.

Installation and optional Hub login

pip install transformers datasets evaluate rouge_score

from huggingface_hub import notebook_login
notebook_login()

Login is useful for uploading/sharing the trained model. Use an access token securely; never hard-code or publish it.

Load and split BillSum

from datasets import load_dataset

billsum = load_dataset("billsum", split="ca_test")
billsum = billsum.train_test_split(test_size=0.2, seed=42)

This creates an 80:20 train/test split. The transcript reports roughly 989 records in the selected subset during preprocessing.

Load T5 tokenizer

from transformers import AutoTokenizer

checkpoint = "google-t5/t5-small"
tokenizer = AutoTokenizer.from_pretrained(checkpoint)

Required preprocessing behavior

The preprocessing function must:

  1. prefix each input with summarize: so a multitask T5 model knows the intended task;
  2. tokenize source bill text;
  3. tokenize target summaries with text_target=;
  4. truncate source and target to their selected maximum lengths;
  5. assign target token IDs to labels.
prefix = "summarize: "

def preprocess_function(examples):
    inputs = [prefix + doc for doc in examples["text"]]
    model_inputs = tokenizer(inputs, max_length=1024, truncation=True)

    labels = tokenizer(
        text_target=examples["summary"],
        max_length=128,
        truncation=True,
    )
    model_inputs["labels"] = labels["input_ids"]
    return model_inputs

tokenized_billsum = billsum.map(preprocess_function, batched=True)

The transcript’s phrase “2 raised to 10” corresponds to a source maximum length of 1024. Targets use 128 tokens. batched=True speeds the mapping operation.

After preprocessing, the remaining workflow is to load a sequence-to-sequence model (AutoModelForSeq2SeqLM), choose a seq2seq data collator/training arguments, fine-tune, evaluate generation using ROUGE, and use the trained model for inference.

Practical use cases

  • summarize legislation for policy analysts;
  • generate executive summaries of long reports;
  • summarize customer-support histories before agent handoff;
  • condense research or legal documents, with human review for factual omissions/hallucinations.

9. Common errors and misconceptions

  1. A Space is only documentation. False: it builds and hosts an executable application.
  2. Users must install a Space locally. False for normal hosted use.
  3. External hosting is always required. False: Spaces supplies hosted runtime infrastructure, subject to its resource tier.
  4. All dependencies belong in requirements.txt. False: system packages belong in packages.txt; pre-install needs may belong in pre-requirements.txt.
  5. Any checkpoint can solve any task. False: architecture, task head, fine-tuning, and domain fit matter.
  6. pipeline() fine-tunes the model. False: it is primarily an inference abstraction.
  7. A small labeled set implies training from scratch. False: it strongly favors transfer learning/fine-tuning.
  8. Good-looking zero-shot text proves accuracy. False: benchmark it.
  9. Prompting always replaces fine-tuning. False: prompting does not update weights and may fail on stable domain alignment.
  10. A DataFrame KeyError is a model problem. False: inspect and correct the data schema.
  11. Conversion to Dataset fixes bad column names. False: validate first.
  12. Sampling with replacement creates new unique information. False: it creates duplicates.
  13. Replacement prevents leakage. False: split discipline and overlap checks prevent leakage.
  14. A balanced test set represents production prevalence. Not necessarily; report performance on both diagnostic-balanced and realistic-distribution test sets when possible.
  15. Higher LoRA rank or batch size automatically improves the weak class. False: determine the bottleneck experimentally.
  16. Warnings about a newly initialized classifier head always indicate failure. False: they are expected when attaching a new task head to a base model.

10. Exam-focused synthesis

High-yield contrasts

Pair Core distinction
Pretraining vs fine-tuning General representation learning vs task/domain adaptation
Prompting vs fine-tuning Change context vs update parameters
Quantization vs LoRA Reduce numerical precision/memory vs learn low-rank task updates
pipeline() vs model + tokenizer Convenience vs detailed control
Extractive vs abstractive summary Select existing text vs generate new text
Oversampling vs leakage Duplicate minority training rows vs improper train/test information overlap
Accuracy vs recall Overall correctness vs coverage of actual class members
Balanced quantity vs diverse data Equal counts do not ensure varied or representative linguistic patterns

Likely long-answer structure: “How would you build a transformer NLP solution?”

  1. Define task, label semantics, stakeholder cost of errors, and deployment constraints.
  2. Acquire reliable labeled data and audit schema, quality, bias, imbalance, duplication, and leakage.
  3. Split before training-only resampling/augmentation.
  4. Select a compatible pretrained checkpoint and tokenizer.
  5. establish a zero/few-shot or frozen-model baseline.
  6. preprocess consistently with padding/truncation and correct target handling.
  7. fine-tune using Trainer/custom training; use PEFT/LoRA and quantization when resources require it.
  8. tune only justified hyperparameters through controlled experiments.
  9. evaluate overall and per class using accuracy, precision, recall, F1, and confusion matrix; use cross-validation where useful.
  10. perform qualitative error analysis, especially on the business-critical class.
  11. choose the smallest intervention supported by evidence, retrain, and reevaluate.
  12. deploy through a Space with correct README metadata and dependency files.
  13. monitor drift, latency, cost, and class-specific errors after deployment.

Final memory hooks

  • Checkpoint fit first: task and domain determine whether adaptation is needed.
  • Schema before model: a broken column contract cannot be repaired by a larger model.
  • Split before oversampling: duplicates are not new information, and replacement is not leakage protection.
  • Accuracy alone is insufficient: inspect per-class recall/F1 and the confusion matrix.
  • Quantization saves memory; LoRA learns adaptation.
  • Understand the error before increasing compute.
  • A Space turns a model repository into a shareable interactive application.
