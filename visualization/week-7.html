Scope and exam orientation

Week 7 marks the transition from visualization theory to practical work with Python. The material covers: setting up Anaconda, Python, and Jupyter Notebook; working with the Jupyter interface; basic Python data types, operators, conditions, and loops; quiz concepts; a data-ingestion case study; and a live review of distribution, part-to-whole, relationship, qualitative, and tabular visualizations.

Instructor emphasis: Knowing only how to create a chart is insufficient. Know the purpose of each chart, its terminology, how humans perceive it, and the circumstances in which it can mislead.

1. Python and Jupyter environment setup

1.1 Prerequisites

The practical visualization work assumes a beginner level and requires:

  • A working Python environment.
  • Jupyter Notebook, the computational notebook used throughout the course.
  • Basic familiarity with Python and the Jupyter interface.

The recommended way to obtain Python and Jupyter together is the Anaconda distribution. Anaconda bundles Python, Jupyter, package-management tools, and many data-science packages.

1.2 Installing Anaconda

Procedure demonstrated (Windows):

  1. Visit the Anaconda download page (anaconda.com/download). Registration may be skipped.
  2. Choose the installer for the computer’s operating system: Windows, macOS, or Linux. The demonstration used the Windows 64-bit graphical installer (about 912 MB at the time of recording).
  3. Wait for the installer to download and run the executable.
  4. Select Next, accept the terms, and use the recommended single-user/Just Me installation.
  5. Retain the default installation location unless there is a specific reason to change it.
  6. Keep the default options. In particular, adding Anaconda to the system PATH can cause conflicts and was marked not recommended; registering Anaconda/Python is sufficient.
  7. Select Install, wait for completion, and select Finish.
  8. The final screen can optionally launch Anaconda Navigator; leave the checkbox selected if immediate launch is desired.

1.3 Anaconda Navigator

Anaconda Navigator is the graphical interface included with Anaconda. It lets a user install and launch Jupyter Notebook, Spyder, and other applications and manage environments without using the command line. This is especially useful for beginners uncomfortable with a command-line interface.

To install Jupyter through Navigator:

  1. Open Anaconda Navigator.
  2. Find Jupyter Notebook among the available applications/packages.
  3. Select Install.
  4. After installation, Jupyter can be launched from Navigator or from the operating-system search.

1.4 What Jupyter Notebook is and why it is used

Jupyter Notebook is a web-browser-based notebook-authoring application: a digital notebook or advanced word processor in which code, explanation, output, and visualization coexist.

It supports:

  • Writing code with syntax assistance and indentation.
  • Executing small pieces of code interactively.
  • Displaying results directly below the code.
  • Writing explanatory notes beside or below code.
  • Exploring and visualizing data.
  • Sharing the complete notebook through an LMS or with collaborators.

This combination makes code easier to teach, test, explain, and reproduce.

1.5 Launch sequence and the local server

  1. Search for Jupyter Notebook in the operating system and launch it. Pinning it to the taskbar is recommended because it will be used frequently.
  2. A terminal/console opens first; then the browser opens the Jupyter dashboard, commonly at a local address such as http://localhost:8888/tree.
  3. localhost means the service is being delivered by the user’s own computer, not by a remote website.
  4. The console is the background Jupyter server. It handles browser requests and notebook execution and acts as the bridge between notebook and server.

Critical caveat: Do not close the Jupyter terminal while using the notebook. Closing it stops the server and the notebook will cease to function.

The terminal also reveals the notebook serving/startup directory. Note this path: the dashboard initially exposes only files and subfolders under that directory. The startup directory can be changed, but that was outside the lesson’s scope.

1.6 Dashboard versus notebook

  • Jupyter dashboard: the launchpad/file manager used to browse, create, rename, and open notebooks and folders. It is not itself a notebook.
  • Jupyter notebook: an individual .ipynb document containing executable and explanatory cells.
  • Kernel: the computational engine/back end connected to a notebook. A Python 3 kernel understands and executes Python code. The instructor’s analogy was that the notebook is like a book while the kernel/back-end package provides the working capability behind it.

1.7 Creating the course folder and first notebook

  1. From the dashboard, select New → Folder.
  2. Rename it as a dedicated course folder (the demonstration used a name similar to Amrita Data Vis Folder). Dedicated storage keeps course files organized.
  3. Open that folder.
  4. Select New → Python 3 to create a notebook connected to the Python 3 kernel.
  5. The notebook initially appears as Untitled. Click the title, enter a meaningful name such as My First Jupyter, and select Rename.
  6. The notebook file extension is .ipynb.

Practical use case: Keep every week’s code and charts in separate subfolders under one course directory so notebooks, datasets, and exported images remain easy to locate.

2. Jupyter Notebook interface and cells

2.1 Cells and kernel

A cell is the basic body/block of a notebook. It can contain code, text, or raw content. Cells organize work into small chunks so that code can be tested incrementally and accompanied by explanations.

The kernel is the notebook’s brain/computational engine. When a cell is run, the kernel processes its code and returns the result. Each notebook is connected to a particular kernel/language.

2.2 Three cell types

Cell type Purpose Result when run
Code Python instructions Kernel executes the code and displays output/errors
Markdown Formatted explanations, headings, notes Markdown is rendered as formatted text
Raw Unprocessed content Content is retained without normal code execution or Markdown rendering

New cells are code cells by default. Use the toolbar cell-type dropdown to change a selected cell to Markdown or Raw.

2.3 Command mode and edit mode

  • Command mode: the cell as an object is selected; notebook-level shortcuts apply. The demonstrated cell background appeared grey.
  • Edit mode: the cursor is inside the cell; typing edits cell contents. Clicking inside changed the cell area to white in the demonstration.

Useful commands demonstrated:

  • A in command mode: insert a cell above.
  • B in command mode: insert a cell below.
  • Toolbar +: add a new cell.
  • Ctrl+Enter: run the selected cell and keep the selection on it.

2.4 First program and execution indicators

print("Hello world")

Running the code cell with Ctrl+Enter displays Hello world below it.

The square brackets to the left indicate execution state/order:

  • [*]: the code is still executing.
  • [n]: execution finished; n records the execution count/order.

Because notebooks can run cells out of top-to-bottom order, execution counts help reveal the actual order in which the kernel processed cells.

2.5 Markdown formatting

After changing a cell to Markdown, enter text and run it to render it.

# Heading 1
## Heading 2
### Heading 3

This is **bold text**.
This is *italic text*.
  • One # creates the largest heading; additional # characters create progressively smaller heading levels.
  • **text** makes text bold.
  • *text* makes text italic.
  • A Markdown reference/cheat sheet can be used for additional formatting.

Common error: Markdown syntax placed in a code cell will be treated as code, not rendered formatting. Convert the cell to Markdown first.

3. Python foundations

3.1 Data type and variable

A data type identifies the kind of value a language can process and therefore which operations are valid for it.

A variable is an alias/name for a memory location where a value is stored. The variable name lets the program access or update that value.

Python is loosely/dynamically typed: unlike languages such as C++, Java, or C#, the programmer does not declare a variable’s type in advance. Python evaluates the type from the assigned value at runtime.

Use print() to display a value and type() to inspect its type.

3.2 Seven data types demonstrated

Type Meaning and syntax Lesson example
str Text in quotes first_name = "Santosh"
int Whole number age = 20
float Number with a fractional/decimal part weight = 70.25
bool Logical True or False married = False
list Ordered collection in square brackets cars = ["Honda", "Toyota", "Suzuki"]
tuple Ordered collection in parentheses days = ("Sunday", "Monday", "Tuesday")
dict Key-value mapping in curly braces days2 = {1: "Sunday", 2: "Monday", 3: "Tuesday"} 
print(first_name)
print(type(first_name))

No explicit str declaration is needed; Python infers it from the quoted value.

3.3 Quantitative and qualitative data

  • Quantitative data: measurable numbers on which arithmetic/statistics are meaningful, e.g., distance, dollars/cost, speed, and time. Store as int or float depending on whether fractional values are possible.
  • Qualitative data: labels/categories such as yes/no or satisfied/dissatisfied. Store as str, or as bool when there are exactly two stable logical states and that encoding is clear.

This distinction controls downstream analysis:

  • Quantitative values support totals, averages, rates, regression, line/scatter plots, and histograms.
  • Qualitative values support grouping, counts, frequency tables, and category-based charts.

3.4 Arithmetic operators

With x = 20 and y = 10:

Operation Operator Example/result
Addition + x + y → 30
Subtraction - x - y → 10
Multiplication * x * y → 200
Division / x / y → 2.0
Modulus/remainder % x % y → 0
Exponentiation ** x ** y → 20 raised to 10

Instructor emphasis: Pay special attention to % (modulus, not percentage here) and ** (exponentiation), because their symbols are less intuitive than the other arithmetic operators.

3.5 Logical operators

Logical operators combine or invert Boolean conditions:

  • x and y: true only if both operands are true.
  • x or y: true if at least one operand is true.
  • not x: reverses the Boolean value.

For x = True, y = False:

  • x and y → False
  • x or y → True
  • not y → True

Business-rule example: Login is allowed if the user is an admin or has paid, but never if suspended:

can_login = (admin or paid) and (not suspended)

Parentheses make the intended grouping explicit. A logical AND audit rule such as logged_in and is_admin records only cases where both are true; in the quiz’s five-user table, only Users 1 and 4 qualified, producing two log entries.

3.6 Comparison operators

Comparison operators compare operands and return a Boolean:

Meaning Operator
Equal ==
Not equal !=
Greater than >
Less than <
Greater than or equal >=
Less than or equal <=

For x = 20, y = 35: x == y is false, x != y is true, x > y is false, and x < y is true.

3.7 Assignment operators

Assignment stores or updates values:

Form Equivalent meaning
r = x + y assign computed result to r
x += y x = x + y
x -= y x = x - y
x *= y x = x * y
x /= y x = x / y
x %= y x = x % y
x **= y x = x ** y

The lesson reset x = 20 and y = 10 before demonstrating each compound operator because one assignment changes x and would otherwise affect later examples.

3.8 Membership operators

Membership tests whether an item belongs to a collection:

  • item in collection
  • item not in collection
days = ("Sunday", "Monday", "Tuesday", "Wednesday", "Thursday", "Friday", "Saturday")
"Sunday" in days       # True
"Xunday" not in days   # True

For exact day validation, use item in days. Avoid day in item or searching in " ".join(days), because those perform substring tests and can wrongly accept inputs such as "Sunday!". item == days is also wrong because it compares one string with the whole tuple.

3.9 Conditional statements

Conditional statements implement decision logic and determine whether code blocks execute. Indentation defines the block.

if: one condition, no required alternative

if 10 > 5:
    print("10 is greater than 5")

if ... else: two alternatives

if 5 > 10:
    print("5 is greater than 10")
else:
    print("5 is not greater than 10")

if ... elif ... else: multiple mutually exclusive alternatives

if x > 10:
    print("over")
elif x < 0:
    print("under")
else:
    print("range")

Only the first matching branch executes. Multiple independent if statements do not form one chain. For example, with x = 12, an if x > 10 followed by a separate if x < 0 ... else can print both over and range, because the else belongs only to the second if.

3.10 Iteration/loops

Iteration statements repeatedly execute a block.

for loop

Use when the collection or number of repetitions is known.

for item in range(5):
    print(item)

Output: 0, 1, 2, 3, 4. range(5) starts at zero and excludes the stop value five.

while loop

Use when repetition should continue while a condition remains true; it stops when the condition becomes false.

c = 0
while c < 10:
    print(c)
    c += 1

Output: 0 through 9. The update is essential; without it, the condition may never become false and the loop can be infinite.

For output 0 through 4, both c < 5 and c <= 4 work, but c < 5 is the clearer conventional boundary. c <= 5 would include 5.

4. Quiz concepts and likely exam traps

4.1 Square-root function: value versus rate of growth

For y = √x, values increase as x increases, but the rate of increase decreases. Equal changes in x produce progressively smaller changes in y (diminishing growth).

  • From x = 1 to 4: √4 − √1 = 2 − 1 = 1.
  • From x = 16 to 19: √19 − √16 ≈ 4.359 − 4 = 0.359.

Both intervals have width 3, but the second vertical change is smaller. Exam trap: larger output values do not imply a larger increase or steeper slope.

4.2 Open-source software

Open-source software makes source code available under a license that may permit inspection, modification, redistribution, and derivative works/forks.

Permissive licenses such as MIT, BSD, and Apache 2.0 support broad reuse, modification, redistribution, and commercial products. Consequently, community contributions, libraries, innovation, and competing forks can grow. Matplotlib’s ecosystem illustrates how an open tool can inspire related visualization tools.

4.3 Entity, attribute, relationship, and table

  • Entity/item: object being described, e.g., a student.
  • Attribute: property of an entity, e.g., student age, height, name, or grade.
  • Relationship: connection between entities, e.g., student enrolled in course.
  • Table: a structure that stores the records and their fields.

Exam trap: In “student age,” the student is the entity and age is the attribute.

4.4 f-strings

Formatted string literals were introduced in Python 3.6.

name = "Alice"
score = 90
print(f"{name} scored {score}")
print(f"Total: {price * quantity:.2f}")

They are more concise/readable and often faster than str.format(), and can evaluate expressions such as len(items), price * quantity, or numeric format specifications like .2f.

4.5 Visualization development is iterative

The recommended process is:

Idea → Prototype → Test → Improve → Final chart

Do not abandon a sound visualization idea merely because implementation is initially difficult, wait until mastering every Python feature, or avoid help. Experiment, simplify, consult classmates/colleagues, and improve iteratively.

5. GreenTech Analytics case study: data ingestion and variable design

5.1 Scenario and stakeholders

GreenTech receives:

  • Field-sensor measurements: distance, dollars/cost, speed, and time.
  • Survey responses: yes/no and satisfied/dissatisfied.

Stakeholder priorities:

  • Alex (developer): simple collection logic, proper variables, and few runtime errors.
  • Priya (project lead): a quick prototype that can demonstrate dollars-spent-versus-time trends.
  • Dr. Chen (data scientist): explicit separation of quantitative and qualitative data before visualization.

5.2 Why correct typing matters

price = "150"
time = "25"
price + time          # "15025", concatenation rather than 175

price = 150
time = 25
price + time          # 175

Mixing a string and number, such as "150" + 20, raises a TypeError. Bad typing causes wrong calculations, repeated conversions, runtime failures, misleading charts, and unreliable statistics.

Recommended semantic types:

  • Dollars/cost: float for totals, averages, and financial charts.
  • Time: numeric (int/float, depending on measurement) for trends, regression, and rates.
  • Distance and speed: usually float for averages, comparisons, and models.
  • Satisfaction/response: str for categories or bool for a clear binary response.

5.3 Strategy comparison

Criterion 1. Everything as strings 2. Type at ingestion 3. Generic dictionaries, parse later
Initial speed Fastest Fast with modest validation Moderate
Runtime safety Poor Best Depends on later parsing
Analysis readiness Poor Best Moderate/poor initially
Repeated conversion Yes No Usually yes
Clarity of quantitative vs qualitative Weak Strong Can be obscured
Best context Disposable proof of concept Normal analytics/prod. pipeline Dynamic schemas, APIs, JSON, ETL

Strategy 1: store everything as raw strings

Advantages: very easy, flexible with unstable formats, and fastest for a temporary mock-up. Disadvantages: every calculation needs conversion, conversions may be forgotten, invalid input fails at runtime, string concatenation can silently create wrong values, and code becomes repetitive.

Use only for an early, temporary proof of concept when calculations are not yet required and input formats are still changing. Convert before analysis/reporting.

Strategy 2: detect/validate type at ingestion

Convert numeric input immediately to int/float and retain categorical input as str/bool. It requires slightly more ingestion logic, but yields immediate calculation ability, cleaner analytics, less repeated work, lower runtime risk, and clearer semantics.

Recommended answer: Strategy 2 best balances Priya’s delivery deadline and Dr. Chen’s data-quality requirement.

Strategy 3: generic list/dictionaries and delayed parsing

Example raw record:

{"distance": "24", "speed": "50", "response": "Satisfied"}

This preserves field context and is flexible for unknown/dynamic schemas, APIs, JSON, or larger ETL systems. However, a dictionary is only a container; it does not solve typing. Delayed conversion adds complexity, can produce inconsistent record types, and postpones the quantitative/qualitative distinction. It is unnecessary for a simple prototype unless schema flexibility is genuinely required.

5.4 Recommended implementation plan

  1. Read each incoming value and retain its field meaning.
  2. Validate whether fields expected to be numeric contain valid numbers; do not rely solely on guessing from appearance when the schema is known.
  3. Convert whole-number fields to int and decimal measurements to float.
  4. Normalize categorical answers (e.g., consistent capitalization/spelling) and store them as str, or map an unambiguous binary answer to bool.
  5. Reject, flag, or separately record invalid/missing input rather than allowing it to contaminate analysis.
  6. Calculate and visualize directly from the clean, typed values.

Practical use case: Convert sensor strings such as "24.6" to 24.6 at ingestion, but normalize a survey response such as " satisfied " to "Satisfied". Then a scatter plot of cost against time and a bar chart of satisfaction counts can be generated without later repair.

5.5 Prototype versus production

  • Prototype: temporary string storage/minimal validation can be acceptable if the purpose is only to demonstrate flow and no numerical calculation is performed.
  • Production/analytical code: validate early, assign consistent types, document variable meaning, and minimize runtime conversion.

Good data engineering balances speed, flexibility, and correctness. Clean foundations become more valuable than a quick but unreliable prototype as soon as analytics begins.

6. Live-session chart review

6.1 Central principle: match chart to purpose

Visualization depends on familiarity with available charts and selecting the right chart for the message. Earlier course categories included:

  • Comparing categories.
  • Showing change over time (line and area charts).
  • Showing distributions (histogram and box-and-whisker plot).
  • Showing part-to-whole.
  • Showing relationships.
  • Showing qualitative data.
  • Showing exact individual values (tables).

The instructor stressed learning a broad chart vocabulary—pie, donut, treemap, scatter plot, sunburst, word cloud, bubble chart, etc.—so the choice is not constrained to bar/line/pie. However, variety is not a goal in itself: always use the most appropriate option. Practice creating charts in Excel, Python, or R so tool unfamiliarity does not discourage the correct choice later.

6.2 Histograms

A histogram reveals the shape of a numerical distribution. Each bar represents a value interval/bin; its height represents the number or proportion of observations within that bin.

Bin selection

  • Too few/wide bins: oversimplifies and flattens the distribution, hiding peaks and internal patterns.
  • Too many/narrow bins: makes individual values/noise appear as spikes and dips, obscuring the general shape and encouraging misleading conclusions.
  • Seek a result that is neither oversimplified nor noisy.
  • A stated rule of thumb is the square-root rule: number of bins ≈ √n, where n is the number of observations. It is a starting point, not a substitute for judgment.

Construction rules

  • Keep bin widths consistent (e.g., 0–10, 10–20, 20–30). The instructor explicitly warned against varying widths in the standard histogram being discussed.
  • Put bin ranges on the x-axis.
  • Put frequency, count, relative frequency, or percentage on the y-axis.
  • Ensure the bins cover the relevant data range and the scale communicates the intended pattern.

Comparing datasets

Normalize before comparing distributions with different sample sizes. A group with 1,000 readings and another with 10,000 readings should be made comparable, such as by plotting relative percentages rather than raw counts.

Exploratory use

Define the analytical goal before drawing the histogram. Try different reasonable bin counts/ranges until the chart satisfactorily addresses that goal. This is legitimate exploratory analysis, not arbitrary manipulation, provided the objective remains explicit.

6.3 Box-and-whisker plot

A box plot compactly summarizes distribution through quartiles, median, spread, whiskers, and outliers.

  • Median (Q2): value below which 50% of observations lie; 50% lie above.
  • First quartile (Q1): value below which 25% lie; 75% lie above.
  • Third quartile (Q3): value below which 75% lie; 25% lie above.
  • Interquartile range: IQR = Q3 − Q1; the box contains the middle 50% of observations.
  • Whiskers: extend toward the lower and upper non-outlying values; long whiskers indicate extended spread/tails.
  • Outliers: unusually distant observations, possibly genuine extremes or “freak”/erroneous readings, shown separately beyond the fences.

Standard outlier fences:

Lower fence = Q1 − 1.5 × IQR
Upper fence = Q3 + 1.5 × IQR

Worked example from class: If Q1 = 30 and Q3 = 90, then IQR = 60; 1.5 × IQR = 90. The lower fence is 30 − 90 = −60, and the upper fence is 90 + 90 = 180. Values below −60 or above 180 are plotted as outliers. The instructor strongly emphasized knowing how Excel/software calculates this, even if the tool performs it automatically.

Important correction of phrasing: “1.5 times the IQR” means 1.5 × IQR beyond Q1 or Q3, not simply 1.5 times an observation and not 1.5 times Q1/Q3.

6.4 Part-to-whole charts: pie and donut

A pie chart is a circle divided into slices, each representing a component’s proportion of the whole. A donut chart removes the center of the pie. Examples include male/female share, age groups in a population, product contribution to profit, or proportions of components in a liquid.

Technical terminology matters, especially when prompting AI: saying “slice” precisely identifies a pie-chart component and avoids ambiguous descriptions. AI can generate the visual, but the analyst must specify correctly and review its work.

Rules/caveats:

  • Components must collectively represent the intended whole—normally 100%, or the complete total count. Missing categories yield an incomplete or misleading whole.
  • Pie charts are popular and familiar; general audiences can quickly understand a broad dominant-versus-small-share message.
  • Small proportions (e.g., 0.5%, 1%, 2%) become narrow, hard-to-read slices.
  • Humans are poor at comparing similar angles, arcs, and areas. Near-equal slices make precise ranking difficult.
  • Labels/percentages help, but without them color and shape may not communicate exact values.
  • A bar chart provides a common baseline and usually makes close comparisons much more accurate.
  • Rotating a pie can align a slice with familiar fractions such as a quarter and sometimes improve rough perception, but does not remove the fundamental limitation.
  • Donut charts remove the central angle but remain similarly weak for precise quantitative comparison.

Instructor recommendation: Pie/donut charts may work for a simple, general-audience overview with few clearly different shares. Avoid them for expert/professional analysis or close comparisons; prefer bars. If the audience disagrees with the presenter’s claimed ranking, attention shifts from the message to debating the chart.

6.5 Treemap and sunburst

  • Treemap: nested rectangles show hierarchical part-to-whole structure. Large colored regions can contain smaller subdivisions, so both higher-level groups and their components are visible.
  • Sunburst chart: concentric rings/sectors show multiple hierarchy levels—a “multi-level pie” appearance, but the correct chart name is sunburst.

Know these options, but choose them only when the hierarchy/part-to-whole message warrants them.

6.6 Relationship charts

  • Scatter plot: plots paired (x, y) observations and makes correlation/relationship visible. An upward pattern—y tending to increase as x increases—indicates positive correlation.
  • Bubble chart: extends a scatter plot; x-position and y-position represent two variables, while bubble size encodes a third (e.g., GDP, another measure, and population size).

The instructor specifically encouraged learning to create bubble charts; ordinary XY scatter plots are already widely familiar.

6.7 Word clouds and qualitative displays

A word cloud sizes words mainly according to frequency in a text: a larger word appeared more often after processing. It does not inherently “read” the article and determine conceptual importance as a human would.

Typical processing described:

  1. Break text into words/tokens.
  2. Remove punctuation and common connecting/stop words.
  3. Reduce variants toward root/stem forms where applicable.
  4. Count occurrences.
  5. Encode higher frequency with larger font size (and sometimes color).

Frequency is used as a proxy for importance, so interpretation must be cautious. The session connected this logic to keyword frequency, older search-engine optimization practices, and modern natural-language preprocessing.

Other qualitative displays include:

  • Repeated icons/pictograms (e.g., male/female icons) to convey category counts.
  • 3D models/icons where appropriate.
  • Quotations paired with the speaker’s image.
  • Word trees.

6.8 Special-purpose diagrams

Data visualization also includes displays designed to communicate structure or process:

  • Network diagrams.
  • Hierarchy diagrams.
  • Project activity diagrams.
  • Flowcharts, including flowcharts that explain program logic before coding.

They qualify as visualization because they communicate a message or relationship visually.

6.9 Tables are visualization tools

Use a table when individual exact values matter and the audience must inspect them. Tables are not inferior to charts; their bad reputation often comes from careless default formatting.

Guidelines mentioned:

  1. Visually separate/offset the header from the body.
  2. Use gridlines judiciously; avoid Excel’s indiscriminate “all borders,” which adds cognitive load.
  3. Right-align numbers so magnitudes/decimal places compare cleanly.
  4. Left-align text for natural reading.
  5. Highlight important outliers with color or another deliberate cue.
  6. Put a shared unit in the header rather than repeating ₹/unit text in every cell when all values use the same unit.
  7. Use an appropriate precision; avoid meaningless excess decimal places.
  8. Guide horizontal or vertical reading through spacing and layout.
  9. Group similar items and demarcate groups with whitespace.
  10. Add in-cell visualizations where appropriate, without obscuring the values.

Core principle: Every line, decimal, unit label, and highlight should earn its place by helping the audience. Remove visual clutter that increases cognitive load without adding information.

7. High-probability exam questions and answer cues

  1. Differentiate dashboard, notebook, cell, kernel, and server. Dashboard manages files; notebook is the .ipynb document; cells hold code/text/raw content; kernel executes language code; the local server/terminal connects browser and execution and must remain running.
  2. Why Anaconda? Convenient bundled Python/data-science environment plus Navigator-based application/environment management.
  3. Explain Python’s typing. Type is inferred from the runtime value; no advance type declaration is required.
  4. Name and exemplify the seven lesson data types. String, integer, float, Boolean, list, tuple, dictionary.
  5. Differentiate =, ==, and in. Assignment, equality comparison, and membership test.
  6. Differentiate if, if–else, and if–elif–else. One optional action, two alternatives, and a mutually exclusive multi-branch chain.
  7. When use for versus while? Known iterable/count versus condition-controlled repetition.
  8. Why type data at ingestion? Prevent runtime/type errors, repeated conversion, silent concatenation, and unreliable analytics.
  9. Why can histogram bin choice mislead? Too few bins hide structure; too many amplify noise. State the square-root rule and the need for exploratory judgment.
  10. Define Q1, median, Q3, IQR, and outlier fences. Include IQR = Q3 − Q1 and Q1 − 1.5IQR, Q3 + 1.5IQR.
  11. Why avoid pie/donut charts for precise comparison? Human angle/arc/area comparison is weak, especially for similar or tiny slices; bars offer a common baseline.
  12. What does bubble size mean? A third variable in a scatter-type chart.
  13. How does a word cloud decide size? Primarily token frequency after text preprocessing, not deep semantic understanding.
  14. When prefer a table? When exact individual values matter; format to minimize cognitive load.

Review-Week Augmentation

Data-type classification for chart choice

  • Qualitative/categorical: labels such as product category, department, country, customer name, or service type; arithmetic on the labels is not meaningful.
  • Quantitative: measurable values such as sales revenue, profit, temperature, population, or salary; arithmetic and numerical summaries are meaningful. Monthly Sales Revenue is the explicit review example.
  • Continuous quantitative: may take any value in a range, such as height, weight, or temperature.
  • Discrete quantitative: countable values, such as customers, products, or defects.
  • Ratio: has a meaningful zero, such as revenue, distance, or weight; zero represents absence of the quantity.

Year caveat — likely exam trap

A year is stored as a number but often functions in visualization as an ordered temporal category/discrete time variable. Its sequence may matter more than ordinary arithmetic treatment. Classify a field by its analytical role and context, not merely its storage type or numeric appearance.
